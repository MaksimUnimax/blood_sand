# SEO / Marketing Strategy — AI-Native Hybrid Search Commerce

Версия: 1.0  
Дата принятия: 2026-08-04  
Статус: **основная стратегия маркетинга, SEO и AI-поиска проекта**

---

## 1. Что принято

Проект объединяет две модели в одну рабочую стратегию:

1. **Hybrid Search Commerce** — собственный сайт является управляемым поисково-коммерческим активом, а Ozon/Wildberries остаются частью воронки и альтернативными точками покупки.
2. **Search-first AI / Alice strategy** — обычный Яндекс SEO и видимость в Алисе AI рассматриваются как одна связанная система; AI-поиск не добавляется потом, а учитывается с самого начала при исследовании спроса, выборе страниц, подготовке фактов, структуре контента и измерении результата.

Рабочее название объединённой стратегии:

> **AI-Native Hybrid Search Commerce**

Смысл:

> Создать собственный поисково-коммерческий актив бренда, который одновременно конкурирует за обычный поиск и за роль источника/товарного предложения в Алисе AI, а продажу завершает там, где пользователю удобнее и бизнесу выгоднее: напрямую на сайте либо через Ozon/Wildberries.

Это не стратегия «сайт против маркетплейсов» и не стратегия «GEO вместо SEO».

---

## 2. Зачем нам сайт в этой стратегии

Сайт нужен, чтобы бренд получил то, чего у него нет при работе только через marketplace:

- собственную видимость в обычном поиске;
- возможность становиться источником Алисы AI;
- собственные информационные и сравнительные страницы;
- полный контроль над товарными фактами и их структурой;
- прямой checkout, если экономика подтверждает его полезность;
- альтернативный путь на Ozon/WB для пользователя, который доверяет marketplace больше;
- собственную аналитику поведения и спроса;
- накопление брендового спроса и owned-media value;
- снижение зависимости от одной торговой платформы.

Маркетплейсы сохраняют сильные стороны:

- горячий коммерческий спрос;
- отзывы и рейтинг;
- привычный checkout;
- привычную логистику;
- возможность завершить покупку через Ozon/WB даже после знакомства с брендом на нашем сайте.

---

## 3. Целевая воронка

Основные пути:

### A. Обычный поиск → сайт → покупка

`Яндекс → товарная/категорийная страница → direct checkout или Ozon/WB`

### B. Обычный поиск → информация → товар

`Яндекс → гайд/сравнение/FAQ → карточка товара → direct checkout или Ozon/WB`

### C. Алиса AI → наш источник → покупательская воронка

`запрос пользователя → Алиса AI → наш материал/товар как источник или предложение → сайт/бренд → direct checkout или Ozon/WB`

### D. Алиса AI без клика → последующая покупка

`Алиса упоминает/использует бренд → пользователь не кликает → позднее ищет бренд или товар → покупает напрямую или на marketplace`

Этот сценарий нельзя измерять только последним кликом, поэтому AI visibility и commerce metrics ведутся раздельно.

---

## 4. Что означает AI-native

AI не считается отдельным «каналом после SEO».

Он влияет на:

- выбор запросов для исследования;
- оценку информационных тем;
- приоритет страниц;
- формат и структуру материалов;
- полноту фактов о товаре;
- внутреннюю связность материалов и товара;
- конкурентный анализ;
- требования к структурированным данным;
- KPI;
- регулярный мониторинг после запуска.

При этом обычная поисковая доступность остаётся фундаментом. Нельзя ухудшать индексируемость или качество страницы ради гипотетического AI-эффекта.

---

## 5. Приоритеты при конфликте

Если SEO, AI, коммерция или объём трафика тянут решение в разные стороны, используется такая иерархия:

1. **Правдивость, полезность и доверие пользователя.**
2. **Экономический результат и коммерческая роль.**
3. **Базовая поисковая доступность и SEO.**
4. **Alice AI / AI visibility.**
5. **Сырой объём трафика и частотность.**

Коротко:

> **Business value > SEO foundation > AI visibility > raw traffic**

Дополнительное правило:

> Если два решения примерно равны по пользовательской ценности, коммерции и SEO, выбирается более **AI-ready** вариант.

Это правило нужно, чтобы AI не оставался декларацией, которую каждый раз откладывают в пользу привычного SEO.

Пример:

- если короткая товарная страница лучше продаёт, не превращаем её в длинную статью ради Алисы;
- вместо этого создаём связанную информационную страницу/FAQ, если вопрос реально важен для поиска или AI;
- если тема имеет небольшой Wordstat, но регулярно участвует в Alice fan-out или AI-ответах коммерческой тематики, низкая частотность не является автоматическим основанием её исключить.

# 6. Главное правило данных: не смешивать происхождение запросов

У проекта не будет одной колонки «частотность» для всего.

Каждый запрос, тема или источник получает provenance — откуда именно он появился.

Обязательные типы происхождения:

| `source_type` | Значение |
|---|---|
| `SEED` | запрос предложен нами для исследования |
| `WORDSTAT` | запрос/формулировка получены из фактических данных Wordstat |
| `SERP_QUERY` | запрос был отдельно проверен в обычном Яндексе |
| `ALICE_INPUT` | исходный запрос, который мы сами отправили Алисе для теста |
| `ALICE_FANOUT_OBSERVED` | дополнительный запрос Алисы, который удалось непосредственно наблюдать |
| `ALICE_FANOUT_INFERRED` | предполагаемый нами fan-out; гипотеза, не факт |
| `ALICE_SOURCE` | страница/домен, реально использованные Алисой как источник в наблюдении |
| `WEBMASTER_SEARCH` | после запуска: реальный запрос, по которому сайт показывался в обычном поиске |
| `WEBMASTER_ALICE` | после запуска: запрос/источник из отчёта видимости сайта в Алисе AI |
| `CUSTOMER_EVIDENCE` | формулировка/вопрос из отзывов, обращений и других пользовательских данных |
| `MARKETPLACE_EVIDENCE` | формулировка/интент, подтверждённые карточками, отзывами или поиском marketplace |

Один запрос может иметь несколько типов происхождения одновременно.

Пример:

`печать велеса значение`

может одновременно быть:

- `WORDSTAT`;
- `SERP_QUERY`;
- `ALICE_INPUT`;
- позже `WEBMASTER_SEARCH`;
- позже `WEBMASTER_ALICE`.

Это усиливает тему, но данные не складываются в одну искусственную «общую частотность».

# 7. Query Evidence Ledger — единый реестр доказательств по запросам

Для каждого значимого запроса/темы создаётся единая запись.

Минимальные поля:

### Идентификация

- `query_id`;
- `query_text`;
- `cluster`;
- `intent`;
- `source_types`;
- `first_seen_at`;
- `last_measured_at`.

### Human demand / Wordstat

- broad 30d;
- phrase/quoted 30d;
- exact-form/operator measurement;
- device split;
- regions;
- dynamics/seasonality;
- related queries;
- дата измерения.

### Ordinary Yandex SERP

- дата/регион/устройство;
- Top-10 URLs/domains;
- тип результата;
- marketplace / independent store / informational;
- товарные блоки;
- тип страницы-лидера;
- ключевые признаки контента.

### Alice AI

- исходный `ALICE_INPUT`;
- наличие AI-ответа;
- сохранённый snapshot/результат наблюдения;
- source domains/URLs;
- тип источника;
- наш сайт присутствует/нет после запуска;
- наблюдаемый fan-out — только если он реально доступен;
- inferred fan-out хранится отдельно и никогда не маркируется как факт;
- дата каждого наблюдения.

### Commercial

- direct commercial intent;
- связь с конкретным SKU;
- связь с Ozon/WB;
- потенциальная роль в assisted sale;
- целевой CTA;
- будущая landing/page job.

### После запуска

- Webmaster impressions;
- clicks;
- CTR;
- average position;
- landing URL;
- Alice visibility / Share of Voice;
- Alice source page;
- Metrika sessions;
- ecommerce events;
- direct orders/revenue/margin;
- outbound Ozon/WB clicks;
- данные об атрибутированных marketplace sales — только где это реально измеримо.

# 8. Как оценивать приоритет темы

Частотность сама по себе не определяет приоритет.

Для каждого кластера ведутся минимум четыре независимые оценки:

- **H — Human demand**: насколько тема подтверждается реальным человеческим спросом;
- **A — Alice importance**: насколько тема важна для AI-ответов/fan-out/source selection;
- **C — Commercial value**: насколько тема связана с выбором/покупкой и дополнительной прибылью;
- **O — Owned-asset value**: насколько тема создаёт долгосрочную собственную ценность бренда — первичные данные, ссылки, экспертность, брендовый спрос, повторное использование.

Оценки не должны автоматически складываться в «магический балл». Они нужны, чтобы видеть причину решения.

Пример:

`тату печать велеса`

может иметь высокий H, но низкий C для нашего товара.

`как закрепить подвеску на зеркале`

может иметь небольшой H, но высокий A/C/O.

Поэтому второй кластер потенциально может получить более высокий приоритет для сайта.

# 9. Что собираем ДО запуска сайта

До появления собственного домена собираем данные, которые помогут решить, что вообще строить.

## 9.1 Wordstat

По приоритетным seed/cluster:

- GetTop;
- broad;
- операторные варианты;
- Dynamics;
- device split;
- Russia / при необходимости регионы;
- related requests/associations с ручной фильтрацией.

Каждый API-съём хранится с:

- исходной командой;
- датой;
- методом;
- регионом;
- устройством;
- сырым ответом;
- интерпретацией отдельно от raw data.

## 9.2 Yandex SERP

Для фиксированного набора запросов:

- Top-10;
- типы страниц;
- marketplace vs independent sites;
- товарные блоки;
- конкуренты;
- факторы, которые можно наблюдать на странице.

Обычный публичный web search не подменяет прямой Yandex SERP measurement.

## 9.3 Alice AI

Для тех же root queries:

- есть ли ответ Алисы;
- какие источники использованы;
- какие типы страниц использованы;
- какие коммерческие/информационные элементы попали в ответ;
- наблюдаемые дополнительные запросы, если доступны;
- несколько наблюдений во времени для важных запросов, потому что один ответ не считается устойчивой статистикой.

## 9.4 Customer / marketplace evidence

Отдельно собираются реальные вопросы покупателей:

- размер;
- материал;
- внешний вид в салоне;
- крепление;
- обратная сторона;
- бусины/шнур;
- нагрев/солнце;
- упаковка/подарок;
- потемнение/уход;
- реальные причины покупки и отказа.

Эти данные используются как отдельный evidence layer, а не как замена поисковой частотности.

# 10. Что собираем ПОСЛЕ запуска сайта

После запуска появляется собственная поведенческая статистика.

## 10.1 Обычный поиск

Через Yandex Webmaster:

- реальные запросы;
- показы;
- клики;
- CTR;
- позиции;
- landing pages;
- регион/устройство, когда доступно.

## 10.2 Alice AI

Через инструменты Yandex Webmaster и регулярные контрольные замеры:

- запросы, где сайт появляется как источник;
- страницы, которые выбирает Алиса;
- Share of Voice;
- конкуренты/другие источники;
- динамика.

Важно:

> использование страницы Алисой как источника не равно человеческому переходу на сайт.

Эти события хранятся отдельно.

## 10.3 Люди на сайте

Через Yandex Metrika и ecommerce events:

- сессии;
- source/medium;
- landing page;
- просмотр товара;
- взаимодействие с фото/контентом, если это действительно нужно для решений;
- переход к checkout;
- direct order;
- revenue;
- клики Ozon/WB;
- возвраты к сайту;
- конверсия по источникам.

## 10.4 Роботы

Роботы не смешиваются с людьми.

Отдельно контролируем:

- обход поисковыми роботами;
- техническую доступность страниц;
- server logs / bot reports, когда это нужно для диагностики.

Нельзя интерпретировать посещение робота как трафик покупателя или AI referral.

---

# 11. Разделение Human / Robot / Alice Source / AI Referral

Четыре разных сущности:

1. **Human search visit** — человек пришёл из обычного поиска.
2. **Robot crawl** — робот Яндекса/другой crawler прочитал страницу.
3. **Alice source usage** — Алиса использовала страницу как источник, даже если человек не кликнул.
4. **Human AI referral** — человек нажал ссылку из AI-интерфейса и пришёл на сайт, если источник перехода можно технически определить.

Нельзя обещать 100% точное определение каждого отдельного AI-referral только по данным сайта. Поэтому AI-эффект оценивается в совокупности:

- Webmaster Alice visibility;
- фактические источники Алисы;
- Metrika/referrer данные;
- брендовый спрос;
- конверсии;
- контрольные наблюдения.

# 12. Базовая структура статистики

Минимально должны существовать отдельные наборы данных:

### A. `query_evidence_ledger`

Единый реестр запросов/тем и их provenance.

### B. `wordstat_measurements`

Каждое измерение Wordstat как отдельная запись; raw results не переписываются итоговыми выводами.

### C. `serp_observations`

Каждый прямой Yandex SERP snapshot с датой/регионом/устройством.

### D. `alice_observations`

Каждый Alice input/output/source snapshot отдельно.

### E. `customer_evidence`

Реальные вопросы/сигналы покупателей с источником.

### F. После запуска: `search_performance`

Webmaster queries/positions/impressions/clicks.

### G. После запуска: `alice_visibility`

Alice SoV/query/source/page data.

### H. После запуска: `commerce_events`

Direct orders, revenue/margin, Ozon/WB outbound clicks и другие события воронки.

### I. `measurement_log`

Что измеряли, когда, каким инструментом, с какими ограничениями.

---

# 13. Правила интерпретации статистики

1. Wordstat count не равен числу покупателей.
2. Broad-count не равен exact demand.
3. Counts вложенных Wordstat-фраз нельзя бездумно складывать.
4. Один ответ Алисы не считается устойчивой частотой/долей.
5. Предполагаемый fan-out не считается наблюдаемым fan-out.
6. Alice source usage не считается человеческим визитом.
7. Human visit не считается продажей.
8. Клик на Ozon/WB не считается подтверждённой marketplace-продажей, если нет доказуемой атрибуции.
9. Трафик не является главной метрикой стратегии.
10. Для динамических данных всегда хранится дата измерения.
11. Raw data и аналитический вывод хранятся раздельно.
12. Любое изменение стратегии должно иметь измеримую причину.

- direct margin;

- impressions;

# 15. Как теперь принимаются решения о страницах и ядре

Новая последовательность обязательна:

1. Определить root user task / seed.
2. Получить Wordstat evidence.
3. Проверить обычный Yandex SERP.
4. Проверить Alice AI по тому же root query.
5. Зафиксировать Alice sources и наблюдаемый fan-out, если доступен.
6. Добавить customer/marketplace evidence.
7. Сгруппировать запросы по реальной задаче пользователя, а не только по словам.
8. Оценить H / A / C / O.
9. Определить page job.
10. Только после этого решать: отдельная страница, блок существующей страницы, FAQ, товарная характеристика или вообще ничего не создавать.
11. После запуска проверять решение по Search + Alice + Commerce данным.
12. Если фактические данные противоречат гипотезе — менять стратегическую реализацию, а не защищать первоначальный план.

---

# 16. Что стратегия запрещает

- собирать ядро только по Wordstat и сразу превращать его в URL;
- делать массовые AI/SEO-страницы без собственного содержания;
- оптимизировать ради трафика без коммерческой/owned роли;
- считать GEO заменой SEO;
- считать SEO-позицию гарантией цитирования Алисой;
- считать AI-упоминание гарантией клика;
- считать клик гарантией продажи;
- подменять прямой Yandex/Alice measurement публичным web search;
- смешивать роботный трафик с человеческим;
- смешивать raw measurements и интерпретации;
- переносить код аналитики в `marketing/` — здесь фиксируются требования и структура данных, реализация позже относится к `site/`.

---

# 17. Ближайшая рабочая последовательность

До дальнейшего массового сбора ядра:

1. закрепить Query Evidence Ledger;
2. использовать уже полученный первый Wordstat API result как первую фактическую запись;
3. продолжить Wordstat не «по всему подряд», а по root-intents стратегии;
4. параллельно подготовить прямой Yandex SERP/Alice capture;
5. затем объединять evidence по каждому кластеру;
6. только после evidence map принимать контентные и структурные решения.
