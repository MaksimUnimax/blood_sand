# Data Architecture — marketing research evidence

Версия: 1.0  
Дата: 2026-08-04  
Статус: **каноническая архитектура хранения исследовательских данных**

Этот документ определяет, где и в каком виде хранятся данные маркетинговых исследований до и после запуска сайта. Его задача — не допустить смешивания первичного доказательства, нормализованных данных, текущего сводного состояния и аналитических выводов.

## 1. Основной поток данных

Канонический поток:

`registry/input → raw evidence → normalized observations → Query Evidence Ledger → derived analysis / decisions`

Каждый слой имеет отдельную роль. Данные не переносятся между слоями путём переписывания смысла исходного наблюдения.

## 2. Слои данных

### 2.1 `registry/` — входные очереди и управляемые списки

Назначение:

- seed-запросы;
- список запросов, которые требуется измерить;
- контролируемые справочники кластеров/источников, если они появятся;
- очереди будущих измерений.

Это **не источник фактической частотности или выдачи**. Наличие строки в registry означает только то, что запрос/объект включён в исследование.

Целевая структура:

```text
marketing/data/registry/
  wordstat_seed_queries.csv
  ...
```

Существующий `marketing/data/wordstat_seed_queries.csv` до миграции считается registry-файлом по смыслу.

### 2.2 `raw/` — первичные неизменяемые доказательства

Назначение:

- точный ответ API;
- прямой capture Yandex SERP;
- прямой capture Alice AI;
- первичный customer/marketplace evidence;
- технические метаданные измерения.

Правило:

> Raw evidence после сохранения не редактируется ради удобства анализа.

Если измерение повторяется, создаётся **новый raw-файл**. Старый не заменяется.

Допустимо хранить рядом с payload технический envelope: время, метод, регион, устройство, HTTP status, request metadata, источник. Аналитические выводы не должны подменять исходный payload.

Целевая структура:

```text
marketing/data/raw/
  wordstat/
  yandex_serp/
  alice/
  customer/
  marketplace/
```

Существующий файл:

`marketing/data/wordstat/2026-08-04_gettop_pechat_velesa_ru_all.json`

считается историческим raw evidence. До миграции его не перемещаем и не переписываем; при проверке пункта 02.5 решается безопасная миграция/ссылка без потери истории.

### 2.3 `normalized/` — структурированные наблюдения

Назначение:

- привести разные raw-источники к стабильной табличной/JSON-схеме;
- одна запись должна описывать конкретное наблюдение;
- сохранить ссылку на исходный raw evidence;
- позволить агрегировать повторные измерения без изменения raw.

Целевая структура:

```text
marketing/data/normalized/
  wordstat/
  yandex_serp/
  alice/
  customer/
  marketplace/
```

Normalized-данные могут быть пересобраны из raw после исправления схемы. При этом raw остаётся источником истины для факта измерения.

### 2.4 `ledger/` — текущее сводное состояние по запросам/темам

Назначение:

- один канонический Query Evidence Ledger;
- связывать query/topic с Wordstat, SERP, Alice, customer/marketplace evidence и будущими Webmaster/Commerce метриками;
- хранить текущую сводную картину и ссылки на наблюдения;
- хранить H/A/C/O оценки и текущее решение.

Целевая структура:

```text
marketing/data/ledger/
  query_evidence_ledger.csv
```

Ledger **не является raw-хранилищем** и не должен содержать весь payload внешних систем.

Существующий:

`marketing/data/query_evidence_ledger_template.csv`

является шаблоном будущего ledger и до миграции сохраняется на текущем пути.

### 2.5 `derived/` — аналитические производные

Назначение:

- opportunity maps;
- сравнительные таблицы;
- приоритизация кластеров;
- scorecards;
- отчёты по H/A/C/O;
- сводки для Page Jobs;
- иные результаты, которые можно повторно вычислить из normalized/ledger.

Целевая структура:

```text
marketing/data/derived/
  opportunities/
  reports/
  snapshots/
```

Derived-файл не является первичным доказательством. Если вывод расходится с raw evidence, приоритет имеет raw + корректно нормализованное наблюдение.

## 3. Правило имён файлов

Для измерений используется UTC-время и стабильный формат имени.

Рекомендуемый шаблон raw-файла:

```text
YYYYMMDDTHHMMSSZ__SOURCE__OPERATION__SUBJECT__REGION__DEVICE.ext
```

Примеры:

```text
20260804T122919Z__wordstat__gettop__pechat-velesa__225__all.json
20260804T130500Z__yandex-serp__top10__pechat-velesa-kupit__225__desktop.json
20260804T131200Z__alice__answer__pechat-velesa-kupit__ru__desktop.json
```

Если два наблюдения технически могут получить одинаковый timestamp, в конец добавляется уникальный suffix/observation id после его формального определения в шаге 02.3.

Правила:

- дата/время raw измерения — UTC;
- текстовые timestamps внутри записи — ISO 8601;
- имя файла должно быть filesystem-safe;
- исходный русский query хранится **внутри данных полностью**, имя файла может использовать нормализованный slug;
- регион и устройство включаются в имя, если они влияют на результат;
- secrets, API keys, access tokens и персональные данные в имени/файле не хранятся.

## 4. Повторные измерения и история

Повторный Wordstat/SERP/Alice capture всегда создаёт новое наблюдение.

Нельзя:

- заменить snapshot от 2026-08-04 snapshot'ом от 2026-09-04;
- переписать старый count новым;
- менять старый Alice source так, будто он был таким изначально;
- превращать `inferred` в `observed` без нового доказательства.

Можно:

- обновить текущее сводное значение в Ledger;
- создать новый derived report;
- отметить старое наблюдение как superseded/invalid, если обнаружена методологическая ошибка, но не удалять сам evidence без отдельной причины.

## 5. Что является источником истины

По уровням:

1. **Raw evidence** — что фактически вернул/показал источник в конкретный момент.
2. **Normalized observation** — структурированное представление raw с явной ссылкой на него.
3. **Ledger** — текущее сводное состояние для принятия решений.
4. **Derived** — аналитическая интерпретация.

Если derived/ledger противоречит raw, требуется исправить нормализацию или сводку; raw не переписывается под вывод.

## 6. Роль существующих файлов

До физической миграции:

- `wordstat_seed_queries.csv` = **registry/input queue**;
- `query_evidence_ledger_template.csv` = **ledger schema template**;
- `yandex_serp_alice_capture_template.csv` = **legacy/current capture template**, окончательная логическая схема будет уточнена в 02.3;
- `data/wordstat/*.json` = **historical raw Wordstat evidence**;
- research `.md` = **interpretation / methodology / decisions**, а не raw data.

Ни один существующий файл не удаляется только ради красивой новой структуры. Миграция выполняется только после проверки ссылок и смысла в 02.5.

## 7. Правило для интерпретаций

Интерпретация хранится отдельно от raw payload либо в явно маркированном поле `derived_note`/`interpretation_note`, которое нельзя путать с ответом источника.

Если raw JSON содержит такой note, он должен быть явно технически отделим от объекта ответа API.

## 8. Версионирование

- Raw snapshots: append-only, каждый capture отдельным файлом.
- Normalized observations: версия схемы должна быть указана в файле/метаданных; пересборка допустима из raw.
- Ledger: обновляется как текущее каноническое состояние; история основана на raw/normalized и Git history.
- Derived reports: датируются, если используются как основание решения.
- Методологии и стратегии: версионируются через Git и датированные изменения документации.
