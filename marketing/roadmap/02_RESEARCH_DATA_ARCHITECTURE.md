# 02 — Архитектура исследовательских данных

Статус: **[~] В РАБОТЕ**  
Дата начала: 2026-08-04  
Оценка: **5 ранов**  
Фактически выполнено: **1/5 ранов**

## Цель пункта

До массового Wordstat-съёма, Yandex SERP/Alice исследования и последующего сведения результатов создать единую архитектуру данных, чтобы каждый новый результат сохранялся один раз, с понятным происхождением, не смешивал raw-данные с интерпретацией и мог быть связан с Query Evidence Ledger.

## Критерий завершения пункта

Пункт считается завершённым, когда:

- определены канонические слои данных и их назначение;
- определены каталоги, имена файлов и правила версионирования/датирования;
- определены обязательные идентификаторы и provenance;
- определены отдельные форматы хранения Wordstat, Yandex SERP, Alice и customer/marketplace evidence;
- определено, как данные попадают в Query Evidence Ledger;
- определены правила обновления без потери истории;
- определены проверки качества/полноты перед переходом к массовому сбору;
- архитектура проверена на пригодность для пунктов 03–05 roadmap.

### Найденные пробелы

1. **Нет формально закреплённых слоёв данных.** Сейчас raw API-result, рабочие CSV и интерпретации существуют, но нет общего правила `raw → normalized → ledger → decisions`.
2. **Нет единого правила имён и идентификаторов измерений.** Нужны устойчивые `query_id`, `measurement_id`/`observation_id`, дата/время, источник и ссылка на raw snapshot.
3. **Нет общего правила повторных измерений.** Нельзя перезаписывать прошлый SERP/Alice/Wordstat snapshot новой датой; история должна сохраняться.
4. **Не определены единые значения пустого/неизмеренного/неприменимого поля.** Пустое значение не должно означать одновременно `0`, `not measured` и `not available`.
5. **Текущий Query Evidence Ledger — хороший сводный шаблон, но он не должен становиться raw-хранилищем.** В него должны попадать нормализованные/сводные данные и ссылки на первичные наблюдения.
6. **`wordstat_seed_queries.csv` частично дублирует будущий Ledger.** Нужно определить его роль как входной очереди/seed registry, а не второй конкурирующей базы истины.
7. **`yandex_serp_alice_capture_template.csv` смешивает SERP-позицию и Alice-source поля в одной строковой модели.** Нужно определить, можно ли сохранить это как capture-формат или разделить наблюдения логически, чтобы несколько Alice sources и Top-10 результатов не порождали неоднозначность.
8. **Raw Wordstat JSON уже содержит краткую interpretation note.** Нужно закрепить правило: raw payload/технические метаданные сохраняются без аналитического переписывания; интерпретация живёт отдельно или явно маркируется как derived note.
9. **Нет формальной связи `source record → query → cluster → page job → decision`.** Стратегия требует её, но схема обновления ещё не описана.
10. **Нет checklist качества перед использованием данных в решениях.** Нужны правила: дата, регион, устройство, источник, статус измерения, raw reference, отсутствие подмены observed/inferred.
