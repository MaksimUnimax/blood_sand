# Ozon — обязательные правила сбора и фиксации данных

Статус: **MANDATORY / READ-BEFORE-COLLECTION**.

Этот файл задаёт обязательный порядок работы AI-диалога, Ozon Bridge и GitHub-хранилища для раздела `продажи/статистика/ozon/` проекта «Кровь и песок».

## Главная цель исполнения

Главная оптимизационная цель — **получить весь требуемый объём данных с минимально возможным количеством пользовательских/диалоговых шагов и минимальным количеством бесполезных записей**, не нарушая ограничений Ozon API и Bridge.

Оптимизировать нужно не число физических provider requests само по себе, а число действий пользователя, количество последовательных AI-turns и объём бесполезной персистенции.

### Обязательные следствия

1. Все независимые `OZON_API_V1` / `OZON_HELP_V2` команды текущего шага группируются в **один command block** и отправляются **одним нажатием Ozon**.
2. Не дробить независимые запросы по отдельным сообщениям без технической необходимости.
3. Для `product_queries_details` при `limit_by_sku=15` и `page_size=100` использовать до **6 SKU на один physical request** (`6 × 15 = 90`) — это безопасный одностраничный чанк.
4. Все независимые чанки одного среза можно и нужно включать в один sequential batch / один command block.
5. Если несколько срезов независимы и их можно отправить без использования свежих opaque values из предыдущего результата, их также разрешено группировать в тот же command block.
6. По одному SKU запрашивать только как **rescue** для доказанного partial/429/особого случая; не использовать single-SKU как обычную схему сбора.
7. Если Bridge/API предоставляет bulk export, report workflow, file attachment или другой способ получить большой набор данных с меньшим числом диалоговых шагов, такой путь **предпочтительнее** множества текстовых запросов при сохранении полноты evidence.
8. Для report workflow использовать только фактические `workflow_continuations[].next_command` и свежие `code/file_ref/cursor/offset/...`; зависимые шаги заранее не батчить.
9. **429, 4xx/5xx, parser/guidance failures и прочие ошибки не являются данными и не записываются в raw/manifest/statistics.**

## НЕМЕДЛЕННАЯ ФИКСАЦИЯ ПОЛЕЗНЫХ РЕЗУЛЬТАТОВ — HARD RULE

**Нельзя переходить к следующему provider batch, пока полезный результат предыдущего batch не зафиксирован в GitHub.**

После каждого `OZON_RESULT_V1` / `OZON_BATCH_RESULT_V1`:

1. Сначала разобрать все результаты batch.
2. Каждый успешный HTTP 200 response со строками немедленно сохранить как raw evidence с точным `request_id` и фактическими строками.
3. HTTP 200 с `total=0` / пустым `queries` сохранить как подтверждённый zero-result в manifest.
4. Немедленно обновить соответствующий manifest/state-файл **только успешными данными/zero-evidence**.
5. Ошибки 429/4xx/5xx/provider/parser **не записывать в GitHub вообще**; использовать их только как временный сигнал для формирования rescue-запроса.
6. Только после успешной фиксации полезного результата формировать следующий Ozon command block.

Хранить реальные полученные данные только в истории диалога и идти дальше **запрещено**.

### Что разрешено сохранять

- HTTP 200 + строки → raw-файл + `PERSISTED`.
- HTTP 200 + `total=0` / пустой `queries` → `PERSISTED_ZERO`; нулевой результат является фактическим evidence.

### Что запрещено сохранять

- HTTP 429 → **не записывать** ни в raw, ни в manifest, ни в отдельный error-файл.
- HTTP 4xx/5xx/provider error → **не записывать** в статистическое/evidence-хранилище.
- Parser/guidance failure с `external_request_executed:false` / `physical_business_request_count:0` → **не записывать**.
- Временные статусы типа `RATE_LIMIT_429`, `COLLECTED_PENDING_RAW_PERSIST`, failed-attempt ledgers и другие служебные попытки не должны засорять канонический manifest.

Канонический manifest предназначен для **успешно сохранённых данных и подтверждённых HTTP 200 zero-results**, а не для журнала ошибок исполнения.

## Точность raw evidence

Для каждого сохранённого ответа обязательно сохранять без переинтерпретации:

- точный `request_id` текущего provider response;
- `chunk_id`;
- фактический `query_index` в том виде, как вернул provider/Bridge — не перенумеровывать;
- `sku`;
- `query`;
- `unique_search_users`;
- `unique_view_users`;
- `view_conversion`;
- `position`;
- `order_count`;
- `gmv`;
- `currency`;
- период и параметры сортировки в manifest.

`null` сохранять как `NULL`, не заменять нулём.

Если порядок возвращённых SKU отличается от порядка запроса, сохранять фактический порядок/`query_index`, а не пересортировывать raw.

## Размер batch и минимизация шагов

Для текущего monthly search workflow:

- target: 76 актуальных SKU;
- `limit_by_sku=15`;
- `page_size=100`;
- safe chunk: максимум 6 SKU → максимум 90 строк;
- 76 SKU → 13 физических chunk requests на один срез;
- эти 13 независимых requests должны по возможности отправляться **одним command block / одним пользовательским действием**;
- если требуется несколько независимых срезов, допускается объединять их независимые envelopes в тот же block, если Bridge/лимиты это позволяют;
- 429/partial закрываются затем **одним grouped rescue block** по всем незакрытым чанкам, а не серией одиночных сообщений;
- failed attempts при этом **не персистятся**.

## Приоритет bulk/report/file workflow

Перед крупным многошаговым сбором проверить, может ли тот же dataset быть получен через:

1. готовый bulk endpoint;
2. create-report;
3. report-info;
4. file reference;
5. file download/attachment.

Если такой workflow даёт тот же или больший объём evidence за меньшее число AI/user turns, использовать его.

Наличие больших файлов/отчётов является нормальным способом передачи данных; не дробить данные на текстовые ответы только потому, что объём большой.

## 429 / rescue

1. На 429 не повторять тот же exact business request автоматически.
2. **429 не сохранять.** Это не бизнес-данные и не evidence.
3. Продолжить другие независимые чанки текущего batch, если Bridge уже выполняет sequential batch.
4. Держать только временный список unresolved SKU/chunks, необходимый для следующего rescue block.
5. После других успешных запросов сформировать один grouped rescue block для unresolved chunks.
6. После успешного HTTP 200 сохранить только успешный результат; историю неудачных 429 в статистический репозиторий не переносить.
7. Срез не считается закрытым, пока каждый целевой SKU не имеет либо успешный HTTP 200 evidence, либо подтверждённый HTTP 200 zero-result.

## Запреты

Запрещено:

- хранить полученные Bridge-данные только в чате;
- запускать следующий batch до фиксации полезного результата предыдущего;
- записывать 429/4xx/5xx/parser failures в raw/manifest/statistics;
- тратить GitHub commits/storage на failed attempts, если они не содержат полезных provider data;
- обычный сбор по одному SKU;
- искусственно разбивать независимые команды на множество AI-turns;
- автоматически повторять exact request после 429/4xx/5xx;
- делать SEO/семантические выводы до закрытия raw collection;
- переписывать raw evidence ради «красивого» порядка или исправлять фактические query strings.

## Порядок каждого рабочего цикла

1. Прочитать этот файл.
2. Проверить текущий manifest/coverage.
3. Определить максимальный набор независимых недостающих запросов.
4. Сформировать **один** command block с максимально полным независимым batch.
5. Получить Bridge result.
6. **Сразу записать только успешные HTTP 200 данные/zero-evidence.**
7. **Не записывать failed attempts.**
8. Проверить, что полезная запись завершена.
9. Только затем формировать следующий grouped batch/rescue.
10. После закрытия raw coverage перейти к derived/analytics layer.

## Критерий правильного поведения AI

Если после получения большого `OZON_BATCH_RESULT_V1` AI сразу выдаёт следующий API batch, не сохранив успешные результаты в GitHub, это нарушение данного правила.

Если AI разбивает независимый полный batch на много отдельных диалоговых шагов без технической зависимости между ними, это нарушение данного правила.

Если AI создаёт commits/manifest rows только ради фиксации 429 или иной ошибки без полезных данных, это нарушение данного правила.

Правильный приоритет:

**МИНИМУМ ДИАЛОГОВЫХ ШАГОВ → МАКСИМУМ НЕЗАВИСИМЫХ КОМАНД В ОДНОМ BLOCK → СОХРАНЯТЬ ТОЛЬКО ПОЛЕЗНЫЕ ДАННЫЕ → НЕ ТРАТИТЬ РЕСУРСЫ НА 429/ОШИБКИ → СЛЕДУЮЩИЙ BATCH.**
