# Marketplace Question Operator — A2 State / SQLite / Telegram Contract

Status: **FROZEN FOR IMPLEMENTATION**  
Date: 2026-08-27

Depends on:

- `MARKETPLACE_QUESTION_OPERATOR_A0_ARCHITECTURE.md`
- `MARKETPLACE_QUESTION_OPERATOR_A1_API_CONTRACTS.md`

This document freezes the state machine, database correlation and Telegram interaction contract before Codex writes application code.

## 1. Core UI principle

There is one **main Telegram card per logical marketplace question** whenever possible.

The main card is edited in place as the question moves through states:

```text
new question
-> manual input / Codex running
-> answer review / error
-> sent / ignored
```

Temporary Telegram messages may be created for reply-based text input, but all important review cards always contain:

```text
Q-ID
marketplace
original buyer question
current answer/error when applicable
```

If editing the old Telegram card fails, the bot may create a replacement card and update `telegram_current_message_id` in SQLite.

## 2. Public question ID

Database row ID is an integer.

Public display ID:

```text
Q-%06d
```

Examples:

```text
id=1   -> Q-000001
id=184 -> Q-000184
```

The Q-ID is generated by backend logic and is not supplied by marketplace or Codex.

## 3. Database schema refinement

A2 adds `answer_revisions` so every Send button can be tied to the exact answer text shown on screen.

### 3.1 `questions`

```sql
CREATE TABLE questions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    public_id TEXT UNIQUE,
    marketplace TEXT NOT NULL CHECK (marketplace IN ('ozon','wildberries')),
    external_question_id TEXT NOT NULL,
    product_id TEXT,
    product_article TEXT,
    product_title TEXT,
    question_text TEXT NOT NULL,
    question_created_at TEXT,
    raw_status TEXT,

    status TEXT NOT NULL,
    current_answer_revision_id INTEGER,
    current_draft_attempt_id INTEGER,

    telegram_question_message_id INTEGER,
    telegram_current_message_id INTEGER,

    external_reply_id TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    sent_at TEXT,

    UNIQUE(marketplace, external_question_id)
);
```

After insert, set `public_id` from the allocated integer ID.

### 3.2 `answer_revisions`

```sql
CREATE TABLE answer_revisions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    question_id INTEGER NOT NULL,
    source TEXT NOT NULL CHECK (source IN ('manual','codex','edited')),
    text TEXT NOT NULL,
    draft_attempt_id INTEGER,
    based_on_revision_id INTEGER,
    created_at TEXT NOT NULL,
    FOREIGN KEY(question_id) REFERENCES questions(id)
);
```

The revision ID is crucial: a stale Telegram Send button must never send a newer/different answer by accident.

### 3.3 `draft_attempts`

```sql
CREATE TABLE draft_attempts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    question_id INTEGER NOT NULL,
    codex_profile TEXT NOT NULL CHECK (codex_profile IN ('codex1','codex2','codex3')),
    status TEXT NOT NULL,
    answer_text TEXT,
    error_type TEXT,
    error_message TEXT,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    FOREIGN KEY(question_id) REFERENCES questions(id)
);
```

### 3.4 `telegram_inputs`

```sql
CREATE TABLE telegram_inputs (
    telegram_prompt_message_id INTEGER PRIMARY KEY,
    question_id INTEGER NOT NULL,
    mode TEXT NOT NULL CHECK (mode IN ('manual_answer','edit_answer')),
    based_on_revision_id INTEGER,
    created_at TEXT NOT NULL,
    expires_at TEXT,
    FOREIGN KEY(question_id) REFERENCES questions(id)
);
```

### 3.5 `settings`

```sql
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Required default:

```text
active_codex_profile = codex1
```

### 3.6 `recent_errors`

Small operator-visible error store:

```sql
CREATE TABLE recent_errors (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    component TEXT NOT NULL,
    error_type TEXT NOT NULL,
    message TEXT NOT NULL,
    question_id INTEGER,
    fingerprint TEXT,
    first_seen_at TEXT NOT NULL,
    last_seen_at TEXT NOT NULL,
    occurrence_count INTEGER NOT NULL DEFAULT 1,
    telegram_notified_at TEXT
);
```

This table is subject to the 5-day technical retention policy.

## 4. Question states

Canonical values:

```text
NEW
MANUAL_INPUT
CODEX_RUNNING
CODEX_ERROR
REVIEW
EDITING
IGNORED
SENDING
SENT
SEND_FAILED
SEND_UNKNOWN
```

There is no automatic approval state.

## 5. Allowed state transitions

### NEW

Allowed:

```text
NEW -> MANUAL_INPUT
NEW -> CODEX_RUNNING
NEW -> IGNORED
```

### MANUAL_INPUT

Allowed:

```text
MANUAL_INPUT -> REVIEW       after valid operator reply
MANUAL_INPUT -> IGNORED
MANUAL_INPUT -> NEW          optional cancel/back
```

### CODEX_RUNNING

Allowed:

```text
CODEX_RUNNING -> REVIEW      successful draft
CODEX_RUNNING -> CODEX_ERROR failure/limit/auth/timeout
```

No Send button exists while Codex is running.

### CODEX_ERROR

Allowed:

```text
CODEX_ERROR -> CODEX_RUNNING retry
CODEX_ERROR -> MANUAL_INPUT
CODEX_ERROR -> IGNORED
```

Changing active Codex profile does not itself change the question state.

### REVIEW

Allowed:

```text
REVIEW -> EDITING
REVIEW -> CODEX_RUNNING      regenerate
REVIEW -> SENDING            explicit Send
REVIEW -> IGNORED
```

### EDITING

Allowed:

```text
EDITING -> REVIEW            after valid operator reply
EDITING -> IGNORED
EDITING -> REVIEW            optional cancel/back to previous revision
```

### SENDING

Allowed:

```text
SENDING -> SENT
SENDING -> SEND_FAILED
SENDING -> SEND_UNKNOWN
```

### SEND_FAILED

Allowed only by explicit operator action:

```text
SEND_FAILED -> SENDING
SEND_FAILED -> REVIEW
SEND_FAILED -> IGNORED       if operator decides not to continue
```

### SEND_UNKNOWN

Do not auto-retry.

Allowed after marketplace reconciliation/operator decision:

```text
SEND_UNKNOWN -> SENT
SEND_UNKNOWN -> SENDING      explicit retry only after no-send is established
SEND_UNKNOWN -> REVIEW
```

### Terminal/local terminal states

```text
SENT
IGNORED
```

`IGNORED` may be reopened later only by an explicit future feature; V1 need not expose reopening.

## 6. Central transition guard

All mutations go through one state transition function/repository method.

Conceptual contract:

```python
transition_question(
    question_id,
    expected_current_state,
    target_state,
    mutation_fields,
)
```

It must update with an expected-state condition inside one SQLite transaction.

If another callback/process already changed the row, return `STALE_STATE` rather than forcing the transition.

## 8. Manual input card

After `Ответить самому`, edit main card to show state, then create a temporary input prompt:

```text
✍️ РУЧНОЙ ОТВЕТ
ID: Q-000184

Вопрос:
<verbatim question>

Ответьте на ЭТО сообщение через Reply.
```

Store its Telegram message ID in `telegram_inputs`.

### Reply rule

A plain operator message that is not a reply to an active `telegram_inputs` message is **not** interpreted as an answer to a question.

This avoids mixing simultaneous questions.

When a valid reply arrives:

1. load `telegram_inputs` by replied-to message ID;
2. load exact question;
3. create `answer_revision(source='manual')`;
4. set question `current_answer_revision_id`;
5. transition `MANUAL_INPUT -> REVIEW`;
6. render review card.

## 9. Review card — manual/edited/Codex

Every review card contains:

```text
ID: Q-000184
Marketplace: ...

Вопрос покупателя:
<verbatim question>

Ответ:
<exact current revision text>

Источник: вручную | codex2 | отредактировано
```

If source is Codex, also show:

```text
🤖 Подготовил: codex2
🟢 Сейчас активен: codex3
```

Buttons:

```text
[✅ Отправить]
[✏️ Редактировать]
[🔄 Сгенерировать заново]
[🚫 Игнорировать]
```

`Сгенерировать заново` may be shown for all REVIEW states; it simply asks current Codex for a new draft based on the same original question.

## 10. Edit input

`Редактировать` creates `telegram_inputs(mode='edit_answer')` tied to:

```text
question_id
based_on_revision_id = current revision id
```

Temporary Telegram input prompt always shows Q-ID, original question and current answer, then asks the operator to Reply.

On valid reply:

1. verify the question still references the expected base revision or handle as stale;
2. create `answer_revision(source='edited', based_on_revision_id=...)`;
3. set as current;
4. transition back to `REVIEW`;
5. render the new exact answer.

## 11. Codex generation

On Codex callback:

1. transactionally verify allowed source state (`NEW`, `REVIEW`, or `CODEX_ERROR` for retry);
2. read `settings.active_codex_profile` in the same logical operation;
3. create `draft_attempt` with captured profile;
4. set `current_draft_attempt_id`;
5. transition to `CODEX_RUNNING`;
6. immediately acknowledge Telegram callback;
7. edit main card to show running status;
8. launch async Codex subprocess.

Duplicate taps while state is already `CODEX_RUNNING` are no-ops with a short Telegram callback notice.

## 12. Codex success

On successful process result:

1. verify the attempt is still the question's current running attempt;
2. mark attempt success;
3. create `answer_revision(source='codex', draft_attempt_id=attempt)`;
4. set revision current;
5. transition `CODEX_RUNNING -> REVIEW`;
6. render question + Codex answer + generating profile + currently active profile.

The Q-ID in the UI comes from the database, not model output.

## 14. Profile selection

Known mapping:

```text
codex1 -> /root/.codex
codex2 -> /root/.codex_second
codex3 -> /root/.codex_third
```

Global selection lives in SQLite `settings`.

Admin `/codex` renders:

```text
🤖 CODEX
Активен: codex2

[codex1]
[codex2 ✓]
[codex3]
```

An error-card `Сменить Codex` button shows the same choices but keeps the question context.

Selecting a profile:

1. updates global `active_codex_profile` transactionally;
2. acknowledges with old -> new;
3. refreshes relevant card;
4. does **not** automatically retry the failed question.

The operator then taps `Повторить через codexN`.

## 15. Send callbacks must be revision-bound

A Send button must encode both:

```text
question_id
answer_revision_id
```

On callback:

1. load question;
2. require `status == REVIEW`;
3. require `current_answer_revision_id == callback.answer_revision_id`;
4. load that exact revision text;
5. transactionally set `SENDING`;
6. only then invoke marketplace adapter.

If the revision is stale, display:

```text
Этот вариант ответа уже устарел. Откройте текущую карточку вопроса.
```

Never substitute the latest answer text for a stale button.

## 16. Telegram callback encoding

Telegram callback data is limited, so use compact integer IDs, not full question text/public IDs.

Suggested canonical forms:

```text
q:<qid>:m                 manual answer
q:<qid>:c                 send to active Codex
q:<qid>:i                 ignore

r:<qid>:<rid>:s           send exact revision
r:<qid>:<rid>:e           edit exact revision
r:<qid>:<rid>:g           regenerate from question
r:<qid>:<rid>:i           ignore

x:<qid>:r                 retry Codex after error
x:<qid>:p                 choose Codex profile for this context

p:<qid>:1                 set active codex1 from question context
p:<qid>:2                 set active codex2
p:<qid>:3                 set active codex3

p:0:1                     global /codex set codex1
p:0:2                     global /codex set codex2
p:0:3                     global /codex set codex3
```

Implementation may use equivalent compact tokens, but they must remain deterministic and under Telegram's callback size limit.

## 17. Ignore callback

`Игнорировать` is local-only.

Transactional action:

```text
allowed source state -> IGNORED
```

Then render:

```text
🚫 ИГНОРИРОВАНО
ID: Q-000184

Вопрос:
...
```

Remove action buttons.

Do not call Ozon/WB write APIs.

## 18. Send success

On confirmed marketplace success:

```text
SENDING -> SENT
```

Store:

```text
external_reply_id if marketplace returns one
sent_at
final revision id remains current
```

Render:

```text
✅ ОТПРАВЛЕНО

ID: Q-000184
Marketplace: ...

Вопрос:
...

Отправленный ответ:
...
```

Remove action buttons.

## 19. Send failure

Definite failure:

```text
SENDING -> SEND_FAILED
```

Render the same Q-ID, original question and attempted answer plus a sanitized error.

Buttons may include:

```text
[🔄 Повторить отправку]
[✏️ Редактировать]
[🚫 Не отвечать]
```

A retry must again use the exact current answer revision.

## 20. Send unknown

If network outcome is ambiguous:

```text
SENDING -> SEND_UNKNOWN
```

The adapter runs marketplace-specific reconciliation from A1.

If confirmed sent:

```text
SEND_UNKNOWN -> SENT
```

If confirmed not sent, offer explicit retry.

If still ambiguous, Telegram says that automatic retry is blocked to avoid a duplicate.

## 21. Active Codex visibility

Show active Codex on:

- initial question card;
- Codex-running card;
- Codex success card;
- Codex error card;
- `/codex` screen.

For an existing draft distinguish:

```text
Подготовил: codex2
Сейчас активен: codex3
```

## 22. Main Telegram commands

V1 minimum:

```text
/start      short help/status
/questions open actionable questions summary
/codex     active profile + switch
/errors    recent coalesced errors
/status    Ozon/WB/Codex/service status
```

No command may expose secrets.

## 23. Operator allowlist

Every Telegram update/callback/message is checked against configured operator user ID.

Unknown Telegram users receive no operational data and cannot invoke actions.

## 24. Error flood control

Fingerprint repeated service errors by at least:

```text
component + error_type + normalized message
```

If the same poll error repeats, update `occurrence_count/last_seen_at` instead of sending a new Telegram alert every poll.

Send a new alert when:

- fingerprint changes;
- previous alert is sufficiently old and the problem remains meaningful;
- error recovers, optionally send one recovery notice.

Codex question-specific errors are not globally suppressed because the operator needs controls for that specific Q-ID.

## 25. Five-day retention implementation

Daily cleanup deletes technical history older than 5 days when it is not currently referenced:

```text
old completed/failed draft_attempts
old superseded answer_revisions except final/current revisions
old telegram_inputs
old recent_errors
old Codex job directories / JSONL / stderr / stdout
```

Never delete:

```text
current answer revision
sent final answer revision
question identity row needed for dedupe
```

## 26. Startup recovery

On daemon startup:

### CODEX_RUNNING

Any attempt left `CODEX_RUNNING` from previous process death is not silently rerun.

Convert to recoverable `CODEX_ERROR` with type:

```text
PROCESS_RESTARTED
```

Telegram retry can then use current active Codex.

### MANUAL_INPUT / EDITING

Keep active input mappings if their Telegram prompt message still exists logically; expired mappings may be cancelled and question returned to `NEW` or `REVIEW` respectively.

### SENDING

Never blindly resend. Convert to reconciliation flow / `SEND_UNKNOWN` and check marketplace state.

## 27. Concurrency

One SQLite database, one daemon.

Use short transactions and WAL mode.

Per-question operations must be serialized logically through expected-state updates.

Long network/Codex calls happen **outside** SQLite write transactions after the state has been claimed.
