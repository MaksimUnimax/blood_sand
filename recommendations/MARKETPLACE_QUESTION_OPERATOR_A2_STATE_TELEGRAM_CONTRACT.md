Status: **FROZEN FOR IMPLEMENTATION — UX CORRECTED**  
Original freeze: 2026-08-27  
Product-owner UX correction: 2026-08-28

Depends on:

- `MARKETPLACE_QUESTION_OPERATOR_A0_ARCHITECTURE.md`
- `MARKETPLACE_QUESTION_OPERATOR_A1_API_CONTRACTS.md`
- `MARKETPLACE_QUESTION_OPERATOR_TELEGRAM_UX_CONTRACT.md`

For Telegram button sets and profile-switch UX, `MARKETPLACE_QUESTION_OPERATOR_TELEGRAM_UX_CONTRACT.md` is the most specific authority.

This corrected A2 removes older contradictory behavior, specifically:

- successful REVIEW regeneration;
- `REVIEW -> CODEX_RUNNING` merely to regenerate a successful answer;
- `/codex` as required profile-switch UX;
- profile switching that is unavailable from some question menus;
- automatic retry immediately after selecting another Codex from `CODEX_ERROR`.

## 1. Core UI principle

There is one main Telegram card per logical marketplace question whenever practical.

Important question UI always contains:

```text
Q-ID
marketplace
original buyer question
current answer/error/state when applicable
active Codex profile when useful
```

Hard invariant:

```text
EVERY QUESTION MENU -> [🤖 Сменить Codex]
```

This applies to NEW, input/running/error/review states and terminal/failure cards.

If an existing Telegram card cannot be edited, the bot may create a replacement projection and update the persisted current Telegram message ID. Canonical business state remains SQLite.

## 2. Public question ID

Database integer row ID maps to:

```text
Q-%06d
```

Examples:

```text
1   -> Q-000001
184 -> Q-000184
```

Q-ID is generated by backend logic and never supplied by marketplace, Codex or Telegram input.

## 3. Database schema

### 3.1 `questions`

```sql
CREATE TABLE questions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    public_id TEXT UNIQUE,
    marketplace TEXT NOT NULL CHECK (marketplace IN ('ozon','wildberries')),
    external_question_id TEXT NOT NULL,
    product_id TEXT,
    product_article TEXT,
    product_title TEXT,
    question_text TEXT NOT NULL,
    question_created_at TEXT,
    raw_status TEXT,

    status TEXT NOT NULL,
    current_answer_revision_id INTEGER,
    current_draft_attempt_id INTEGER,

    telegram_question_message_id INTEGER,
    telegram_current_message_id INTEGER,

    external_reply_id TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    sent_at TEXT,

    UNIQUE(marketplace, external_question_id)
);
```

After insert, derive `public_id` from allocated integer ID.

### 3.2 `answer_revisions`

```sql
CREATE TABLE answer_revisions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    question_id INTEGER NOT NULL,
    source TEXT NOT NULL CHECK (source IN ('manual','codex','edited')),
    text TEXT NOT NULL,
    draft_attempt_id INTEGER,
    based_on_revision_id INTEGER,
    created_at TEXT NOT NULL,
    FOREIGN KEY(question_id) REFERENCES questions(id)
);
```

Every displayed/sent answer is immutable as a revision. A Send button binds an exact revision ID.

### 3.3 `draft_attempts`

```sql
CREATE TABLE draft_attempts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    question_id INTEGER NOT NULL,
    codex_profile TEXT NOT NULL CHECK (codex_profile IN ('codex1','codex2','codex3')),
    status TEXT NOT NULL,
    answer_text TEXT,
    error_type TEXT,
    error_message TEXT,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    FOREIGN KEY(question_id) REFERENCES questions(id)
);
```

Each attempt captures its profile at start. Later global profile changes never rewrite that historical value.

### 3.4 text-input correlation

Implementation must persist enough information to correlate manual/edit text to the exact question and, for edit, the exact base revision.

A compatible schema is:

```sql
CREATE TABLE telegram_inputs (
    telegram_prompt_message_id INTEGER PRIMARY KEY,
    question_id INTEGER NOT NULL,
    mode TEXT NOT NULL CHECK (mode IN ('manual_answer','edit_answer')),
    based_on_revision_id INTEGER,
    created_at TEXT NOT NULL,
    expires_at TEXT,
    FOREIGN KEY(question_id) REFERENCES questions(id)
);
```

This table may remain if reply-message correlation is the safest implementation mechanism. However, the **product UX is not defined as “ForceReply workflow”**. The product requirement is deterministic exact-Q-ID input correlation.

Uncorrelated operator text must never become a marketplace answer.

### 3.5 `settings`

```sql
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Required:

```text
active_codex_profile = codex1 | codex2 | codex3
```

### 3.6 `recent_errors`

A small operator-visible store remains valid:

```sql
CREATE TABLE recent_errors (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    component TEXT NOT NULL,
    error_type TEXT NOT NULL,
    message TEXT NOT NULL,
    question_id INTEGER,
    fingerprint TEXT,
    first_seen_at TEXT NOT NULL,
    last_seen_at TEXT NOT NULL,
    occurrence_count INTEGER NOT NULL DEFAULT 1,
    telegram_notified_at TEXT
);
```

Technical error history is subject to retention policy.

## 4. Canonical question states

```text
NEW
MANUAL_INPUT
CODEX_RUNNING
CODEX_ERROR
REVIEW
EDITING
IGNORED
SENDING
SENT
SEND_FAILED
SEND_UNKNOWN
```

A temporary Telegram profile-choice/confirmation screen does not need a new canonical question state. Selecting a Codex profile changes the global setting, not the question state.

## 5. Allowed state transitions

### NEW

```text
NEW -> MANUAL_INPUT
NEW -> CODEX_RUNNING
NEW -> IGNORED
```

Profile switch:

```text
NEW -> NEW
```

in the sense that only `active_codex_profile` changes; no question mutation is required.

### MANUAL_INPUT

```text
MANUAL_INPUT -> REVIEW       after valid manual answer revision
MANUAL_INPUT -> IGNORED      explicit ignore if offered
```

Profile selection changes no question state.

### CODEX_RUNNING

```text
CODEX_RUNNING -> REVIEW      successful current attempt
CODEX_RUNNING -> CODEX_ERROR failed current attempt
```

Profile selection while running changes only future active profile. The current attempt continues with its captured profile.

### CODEX_ERROR

```text
CODEX_ERROR -> CODEX_RUNNING    explicit Повторить
CODEX_ERROR -> CODEX_RUNNING    explicit Перегенерировать after profile-change confirmation
CODEX_ERROR -> MANUAL_INPUT
CODEX_ERROR -> IGNORED
```

Important:

```text
selecting another Codex profile alone DOES NOT transition to CODEX_RUNNING
```

### REVIEW

```text
REVIEW -> EDITING
REVIEW -> SENDING            explicit revision-bound Send
REVIEW -> IGNORED
```

Explicitly forbidden:

```text
REVIEW -> CODEX_RUNNING      // no successful-answer regeneration in V1
```

### EDITING

```text
EDITING -> REVIEW            after valid edited revision
```

Profile switch changes no question state.

### SENDING

```text
SENDING -> SENT
SENDING -> SEND_FAILED
SENDING -> SEND_UNKNOWN
```

### SEND_FAILED

```text
SEND_FAILED -> SENDING       explicit revision-bound retry
```

No blind automatic retry.

### SEND_UNKNOWN

Marketplace reconciliation from A1 decides the safe path:

```text
SEND_UNKNOWN -> SENT         confirmed sent
SEND_UNKNOWN -> SENDING      only after confirmed not-sent + explicit operator retry
```

No blind retry while outcome remains ambiguous.

### Local/terminal views

`SENT` and `IGNORED` remain terminal for the question workflow in V1, but their Telegram cards still expose `🤖 Сменить Codex` because profile switching is global configuration, not question reopening.

## 6. Central transition guard

All canonical question state mutations go through one expected-state transactional guard, conceptually:

```python
transition_question(
    question_id,
    expected_current_state,
    target_state,
    mutation_fields,
)
```

If another action changed the row first, return stale-state rather than forcing a transition.

Profile selection updates `settings.active_codex_profile` transactionally but does not abuse question state transitions.

## 7. Exact NEW card

Render at minimum:

```text
Marketplace
ID: Q-000184
Marketplace ID
product info if available
original buyer question
active Codex profile
```

Exact buttons:

```text
[✍️ Ответить самому]
[🤖 Отправить в Codex]
[🚫 Игнорировать]
[🤖 Сменить Codex]
```

`Отправить в Codex` captures the active profile when the attempt is successfully claimed.

## 8. Manual input

After `✍️ Ответить самому`:

1. validate operator and exact question;
2. claim `NEW -> MANUAL_INPUT` (or allowed error-to-manual transition);
3. establish deterministic text-input correlation for that Q-ID;
4. render/ask for the operator's manual text;
5. keep `🤖 Сменить Codex` available.

When valid text arrives:

1. resolve the exact question from persisted correlation;
2. create `answer_revision(source='manual')`;
3. set it current;
4. transition `MANUAL_INPUT -> REVIEW`;
5. render exact question + manual answer + REVIEW buttons.

The manual text is **not** sent to the marketplace merely because it was entered.

## 9. REVIEW — one canonical successful-answer menu

Manual, Codex and edited revisions converge on the same review contract.

Render:

```text
ID: Q-000184
Marketplace
original buyer question
exact current answer
answer source
Codex generating profile when source=codex
active profile when useful
```

Exact buttons:

```text
[✅ Отправить]
[✏️ Редактировать]
[🚫 Игнорировать]
[🤖 Сменить Codex]
```

Hard prohibition:

```text
NO [Сгенерировать]
NO [Сгенерировать заново]
NO [Перегенерировать]
```

in successful REVIEW.

No callback action for successful-answer regeneration should exist in the V1 renderer/state contract.

## 10. Edit input

`✏️ Редактировать` is revision-bound.

Input correlation stores:

```text
question_id
mode=edit_answer
based_on_revision_id=current revision id
```

On valid edit text:

1. verify base revision is still the expected/current revision;
2. create `answer_revision(source='edited', based_on_revision_id=...)`;
3. set it current;
4. transition back to REVIEW;
5. render exact edited answer with the same four REVIEW buttons.

During edit input, `🤖 Сменить Codex` remains available and changes only the global profile.

## 11. Codex generation

From NEW or an explicitly authorized CODEX_ERROR retry path:

1. validate question/state;
2. capture `settings.active_codex_profile`;
3. create `draft_attempt` for exact Q-ID;
4. set `current_draft_attempt_id`;
5. transition to `CODEX_RUNNING`;
6. acknowledge callback promptly;
7. render running state;
8. launch async Codex subprocess.

The running card includes:

```text
[🤖 Сменить Codex]
```

Duplicate taps after a running attempt is claimed do not create another attempt.

## 12. Codex success

On success:

1. verify attempt is still current;
2. mark attempt success;
3. create `answer_revision(source='codex', draft_attempt_id=attempt)`;
4. set it current;
5. transition `CODEX_RUNNING -> REVIEW`;
6. render the canonical REVIEW menu.

The successful REVIEW has no generate/regenerate action.

## 13. CODEX_ERROR

Render at minimum:

```text
Q-ID
Marketplace
original buyer question
failed profile
sanitized error
active profile
```

Exact buttons:

```text
[🔄 Повторить]
[✍️ Ответить самому]
[🚫 Игнорировать]
[🤖 Сменить Codex]
```

### `Повторить`

`🔄 Повторить`:

1. uses the profile active when the callback is claimed;
2. creates a new attempt for the same Q-ID;
3. moves to `CODEX_RUNNING`;
4. does not create another question row/Q-ID.

## 14. Profile selection from normal states

Every question menu exposes `🤖 Сменить Codex`.

Profile chooser:

```text
🤖 СМЕНИТЬ CODEX
Сейчас: codex2

[codex1]
[codex2 ✓]
[codex3]
```

From every state except the special CODEX_ERROR flow, profile selection:

1. updates `active_codex_profile`;
2. acknowledges old -> new;
3. returns to the same question/state/menu;
4. creates no attempt;
5. runs no Codex process;
6. performs no marketplace call.

There is no required `/codex` operator command for this behavior.

## 15. Special profile selection from CODEX_ERROR

This is a mandatory two-step flow.

```text
CODEX_ERROR
 -> Сменить Codex
 -> choose codex1/codex2/codex3
 -> persist new active profile
 -> show confirmation menu
```

Profile selection itself does **not** retry.

The confirmation menu contains exactly:

```text
[🔄 Перегенерировать]
[✍️ Ответить самому]
[🚫 Игнорировать]
[🤖 Сменить Codex]
```

The question remains logically in `CODEX_ERROR` until another action is claimed.

Only `🔄 Перегенерировать`:

1. validates the same Q-ID is still in CODEX_ERROR;
2. captures the newly active profile;
3. creates a new draft attempt;
4. transitions `CODEX_ERROR -> CODEX_RUNNING`;
5. launches Codex.

This is the **only** V1 user-facing `Перегенерировать` action.

## 16. Callback identity contract

Callback payloads must be compact, deterministic, within Telegram limits and bind all identity required by the action.

Required identity semantics:

```text
manual: question_id
codex start: question_id
ignore: question_id + expected state/revision where applicable
send: question_id + answer_revision_id
edit: question_id + answer_revision_id
retry codex: question_id
switch profile: originating question context + target profile
error-confirm regenerate: question_id + profile/error context sufficient to reject stale action
retry send: question_id + answer_revision_id
```

Do not retain a successful-review regenerate callback action.

Legacy/stale callback forms must fail closed and be acknowledged without business mutation.

## 17. Send callback — exact revision only

A Send button encodes:

```text
question_id
answer_revision_id
```

Handler:

1. load question;
2. require `status == REVIEW`;
3. require `current_answer_revision_id == callback.answer_revision_id`;
4. load that exact revision text;
5. transactionally claim `SENDING`;
6. acknowledge callback promptly;
7. invoke marketplace adapter;
8. record final/reconciliation state.

Never silently substitute the latest answer for a stale button.

## 18. Ignore

`🚫 Игнорировать` is local only.

No Ozon answer create. No WB answer PATCH/state-none action.

Render IGNORED state and retain:

```text
[🤖 Сменить Codex]
```

## 19. Send success

Confirmed marketplace result:

```text
SENDING -> SENT
```

Store marketplace reply identity when available, `sent_at` and final revision relationship.

Render sent question + exact sent answer and:

```text
[🤖 Сменить Codex]
```

## 20. SEND_FAILED

Definite failure:

```text
SENDING -> SEND_FAILED
```

Render exact Q-ID, question, attempted revision and sanitized error.

Required buttons:

```text
[🔄 Повторить отправку]
[🤖 Сменить Codex]
```

Retry is bound to the exact current revision and passes through the same double-send guards.

## 21. SEND_UNKNOWN

Ambiguous marketplace outcome:

```text
SENDING -> SEND_UNKNOWN
```

Run A1 marketplace-specific reconciliation.

While still ambiguous:

```text
[🤖 Сменить Codex]
```

No blind send retry.

If reconciliation confirms not sent, an explicit safe retry may be exposed according to A1/runtime policy.

## 22. SENDING

The SENDING projection exposes:

```text
[🤖 Сменить Codex]
```

Changing active Codex profile does not affect the in-flight marketplace operation.

## 23. Menu matrix — exact acceptance contract

| State/menu | Required actions |
|---|---|
| NEW | `✍️ Ответить самому`, `🤖 Отправить в Codex`, `🚫 Игнорировать`, `🤖 Сменить Codex` |
| MANUAL_INPUT | manual text-entry interaction + `🤖 Сменить Codex` |
| CODEX_RUNNING | `🤖 Сменить Codex` |
| CODEX_ERROR | `🔄 Повторить`, `✍️ Ответить самому`, `🚫 Игнорировать`, `🤖 Сменить Codex` |
| CODEX_ERROR after profile selection | `🔄 Перегенерировать`, `✍️ Ответить самому`, `🚫 Игнорировать`, `🤖 Сменить Codex` |
| REVIEW | `✅ Отправить`, `✏️ Редактировать`, `🚫 Игнорировать`, `🤖 Сменить Codex` |
| EDITING | edit text-entry interaction + `🤖 Сменить Codex` |
| IGNORED | `🤖 Сменить Codex` |
| SENDING | `🤖 Сменить Codex` |
| SENT | `🤖 Сменить Codex` |
| SEND_FAILED | `🔄 Повторить отправку`, `🤖 Сменить Codex` |
| SEND_UNKNOWN | `🤖 Сменить Codex` |

No implementation or acceptance prompt may add a successful-review generate/regenerate action to this matrix.

## 24. Durable/replay semantics

Telegram transport/replay hardening may evolve in runtime implementation, but business actions must stay idempotent/replay-safe:

- durable duplicate Update must not create duplicate answer revisions/attempts/sends;
- stale callbacks fail closed;
- projection/ack failure after a canonical business mutation must not roll that mutation back or make replay repeat a marketplace/Codex business effect;
- input consumption + revision creation + state transition should be atomic where practical;
- no fake Telegram message ID/correlation may be invented after ambiguous message creation.
