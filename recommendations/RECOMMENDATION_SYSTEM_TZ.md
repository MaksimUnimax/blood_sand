# ТЗ — система рекомендаций славянских оберегов по дате рождения

Версия: 0.1  
Статус: рабочее ТЗ до разработки  
Бренд: «Кровь и Песок»

## 1. Цель

Создать детерминированную систему, которая внутри VK получает от клиента минимальный набор данных и рекомендует один, в исключительном случае два, славянских оберега из актуального ассортимента «Кровь и Песок».

Система должна быть общей для будущих интерфейсов:

- VK Community Bot;
- VK Mini App;
- возможных последующих внутренних интерфейсов.

UI не должен содержать собственную независимую логику подбора. Все каналы используют одну и ту же recommendation matrix.

## 2. Scope V1

### Входит

- только семейство `slavic_symbols_oberegs`;
- 16 Чертогов Сварожьего круга в зафиксированной продуктовой календарной конвенции `KIP_CHERTOG_CALENDAR_V1`;
- подбор по `day + month + gender`;
- один основной результат;
- максимум один дополнительный результат в заранее утверждённых случаях;
- объяснение результата через Чертог и выбранное основание;
- привязка recommendation identity к реальному SKU каталога.

### Не входит

- знаки зодиака;
- Футарк, руны и скандинавские товары;
- православные, патриотические, универсальные и автомобильные товары;
- нумерология;
- свободный AI-выбор товара;
- рекомендации по продажам/популярности;
- roadmap реализации;
- правила замены при отсутствии товара на складе — должны быть утверждены отдельно.

## 3. Входные данные

Минимальный обязательный ввод:

```text
birth_day: 1..31
birth_month: 1..12
gender: male | female
```

`birth_year` для расчёта не нужен и в V1 не запрашивается.

Система обязана валидировать существование календарной даты. Для февраля допускается 29.02 без необходимости знать год: в продуктовой логике это допустимый день и он относится к Чертогу Волка.

## 4. Календарное правило

Используется только версия `KIP_CHERTOG_CALENDAR_V1`, описанная в `RECOMMENDATION_MATRIX.md`.

Критическое правило границ:

> Первый день следующего диапазона относится к новому Чертогу.

Примеры:

- 19.09 → Дева;
- 20.09 → Вепрь;
- 10.10 → Вепрь;
- 11.10 → Щука;
- 06.01 → Ворон;
- 07.01 → Медведь.

Внешние интернет-таблицы во время runtime не запрашиваются. Изменение календаря возможно только новой версией матрицы.

## 5. Алгоритм V1

```text
1. Получить day, month, gender.
2. Провалидировать дату и gender.
3. Определить chertog_id по KIP_CHERTOG_CALENDAR_V1.
4. Найти строки matrix, где chertog_id + gender совпадают с запросом.
5. Отсортировать по rank ASC.
6. Вернуть rank=1.
7. Вернуть rank=2 только если такая строка явно существует в утверждённой матрице.
8. Никогда не генерировать третий результат.
```

Никакого runtime scoring, LLM-ranking и коммерческого reranking в V1 нет.

## 6. Ограничение количества результатов

Это hard product rule:

```text
MIN_RESULTS = 1
MAX_RESULTS = 2
DEFAULT_RESULTS = 1
```

В текущей матрице два результата разрешены только для:

```text
chertog = medved
gender = male
```

Результаты:

1. `Сварог` — `DIRECT_PATRON`;
2. `Медвежья лапа` — `DIRECT_CHERTOG_SYMBOL`.

Добавление второго результата в любой другой сценарий требует изменения версии матрицы, а не эвристики в коде.

## 7. Гендерная политика

Gender — фильтр до выдачи.

Система не должна сначала выбрать запрещённый товар, а затем объяснять клиенту, почему он не подходит.

Жёсткие V1-ограничения описаны в `PRODUCT_CLASSIFICATION.md`.

Примеры:

- `Жива` не выдаётся мужчине;
- `Макошь` не выдаётся мужчине;
- `Звезда Лады` не выдаётся мужчине;
- `Родимич` не выдаётся женщине;
- `Колядник` не выдаётся женщине;
- `Знич` не выдаётся женщине;
- `Всеславец` не выдаётся женщине;
- `Медвежья лапа` не выдаётся женщине в V1;
- `Сварог` и `Перун` могут выдаваться женщине при прямом соответствии покровителю Чертога.

## 8. Нормализация товарной идентичности

Marketplace-name и recommendation identity не обязаны совпадать.

Критический кейс:

```text
marketplace_name: "Печать Велеса"
recommendation_identity: "Медвежья лапа"
```

Для рекомендательной системы эта позиция рассматривается как Медвежья лапа.

Следствия:

- `medved + male` → разрешена как второй результат;
- `volk + male/female` → запрещена;
- название `Печать Велеса` само по себе не создаёт связь с Велесом/Волком.

Реальный SKU/product_id должен храниться отдельно от отображаемой recommendation identity.

## 9. Типы оснований

Допустимые enum:

```text
DIRECT_PATRON
DIRECT_DERIVED
DIRECT_CHERTOG_SYMBOL
CURATED_GENDER_SUBSTITUTE
CURATED_MEANING_SUBSTITUTE
```

Приоритет типов нужен для объяснимости и будущего аудита, но в V1 **не используется для runtime scoring**, потому что rank уже утверждён матрицей.

## 10. Data model

Рекомендуемое разделение данных.

### `chertog_calendar`

```text
calendar_version
chertog_id
chertog_name
patron_name
start_month
start_day
end_month
end_day
```

### `product_policy`

```text
product_id
sku
marketplace_name
recommendation_identity
gender_policy
active_for_recommendation
```

### `recommendation_matrix`

```text
matrix_version
chertog_id
gender
rank
product_id
recommendation_identity
relation_type
reason_code
active
```

`rank` допускает только `1` или `2`.

Уникальность:

```text
UNIQUE(matrix_version, chertog_id, gender, rank)
```

## 11. Reason codes

Для логов и UI-текстов желательно использовать стабильные reason codes, а не хранить бизнес-логику в свободном тексте.

Примеры:

```text
PATRON_EXACT
PATRON_DERIVED
CHERTOG_SYMBOL_EXACT
GENDER_SUBSTITUTE_LINEAGE
GENDER_SUBSTITUTE_HARMONY
MEANING_SUBSTITUTE_ORDER
MEANING_SUBSTITUTE_PROTECTION
MEANING_SUBSTITUTE_SPIRITUAL
MEANING_SUBSTITUTE_LIFE_FIRE
```

Человеческая формулировка может меняться без изменения recommendation result.

## 12. Клиентский ответ

В текущем этапе фиксируется структура, но не окончательный copywriting.

Ответ должен содержать:

1. дату, к которой выполнен подбор, если это уместно в конкретном UI;
2. один или максимум два рекомендуемых товара;
3. название Чертога;
4. короткое нейтральное объяснение основания.

Не нужно:

- предлагать ещё 3–5 альтернатив;
- дописывать несвязанные свойства товара;
- обещать доказанный физический/лечебный/магический эффект;
- автоматически звать клиента «узнать больше», если UX этого не требует.

Пример нейтральной структуры для 13.10:

```text
Для даты 13.10 рекомендуем:

Мужчине — оберег «Родимич».
Женщине — оберег «Макошь».

Эта дата относится к Чертогу Щуки, который в нашей системе связывается с родом, семьёй, мудростью и ответственностью за близких.
```

Формулировки будут утверждаться отдельно.

## 13. Что запрещено алгоритму

- Выдавать больше двух товаров.
- Добавлять «похожие» товары из каталога без строки в матрице.
- Использовать `ordered_units`, revenue, CTR, рекламу или популярность для изменения результата.
- Подменять отсутствующий primary самым продаваемым SKU.
- Использовать marketplace-name как семантический источник, если задана отдельная recommendation identity.
- Определять пол клиента по имени или другим косвенным признакам.
- Менять Чертог через внешний API/LLM.
- Использовать год рождения как нумерологический фактор.

## 14. Политика unavailable товара

В V1 не определена автоматически.

Если рекомендованный SKU отсутствует, движок должен вернуть отдельный статус, например:

```text
RESULT_PRODUCT_UNAVAILABLE
```

а не самостоятельно перейти к резервному товару.

Политика `unavailable → replacement` должна быть отдельно спроектирована и утверждена в roadmap/implementation design.

## 15. Acceptance criteria

### AC-01 — один результат по умолчанию

Для любого валидного сочетания `day + month + gender`, кроме явно разрешённого исключения, возвращается ровно один товар.

### AC-02 — максимум два

Ни один запрос не возвращает более двух результатов.

### AC-03 — Медведь / мужчина

Для `15.01 + male`:

```text
chertog = medved
1 = Сварог
2 = Медвежья лапа
```

### AC-04 — Медведь / женщина

Для `15.01 + female`:

```text
chertog = medved
1 = Сварог
```

Второго результата нет.

### AC-05 — Волк

Для `15.03 + male` и `15.03 + female`:

```text
chertog = volk
1 = Велес
```

`Медвежья лапа` не появляется.

### AC-06 — Щука

Для `13.10 + male`:

```text
chertog = shchuka
1 = Родимич
```

Для `13.10 + female`:

```text
chertog = shchuka
1 = Макошь
```

### AC-07 — Раса

Для `13.08` обоих полов:

```text
chertog = rasa
1 = Даждьбог
```

### AC-08 — гендерный hard filter

Ни один `female` запрос не возвращает товары с `gender_policy=male`; ни один `male` запрос не возвращает товары с `gender_policy=female`.

### AC-09 — граничные даты

- 19.09 → Дева;
- 20.09 → Вепрь;
- 10.10 → Вепрь;
- 11.10 → Щука;
- 23.11 → Лебедь;
- 24.11 → Змей;
- 06.01 → Ворон;
- 07.01 → Медведь;
- 26.08 → Раса;
- 27.08 → Дева.

### AC-10 — детерминизм

Одинаковые входы при одной версии матрицы всегда дают одинаковый результат независимо от канала (бот или Mini App).

## 16. Версионирование

Минимальные идентификаторы:

```text
calendar_version = KIP_CHERTOG_CALENDAR_V1
product_policy_version = KIP_PRODUCT_POLICY_V1
matrix_version = KIP_RECOMMENDATION_MATRIX_V1
```

Изменение календарной границы, gender policy, primary/secondary результата или relation type должно приводить к новой версии соответствующей сущности.

## 17. Открытые вопросы перед roadmap

Они не блокируют фиксацию текущей матрицы, но должны быть решены перед production-разработкой:

1. Где хранится master mapping `recommendation_identity → Ozon/WB/VK product link`.
2. Как определяется актуальная доступность товара.
3. Что делать при unavailable primary.
4. Нужен ли сохранённый результат в сообщениях сообщества после Mini App.
5. Какой канал является первым MVP: бот, Mini App или гибрид.
6. Какие analytics events и conversion events сохранять.
7. Финальные тексты ответов для 32 сочетаний `16 Чертогов × 2 пола`.

Roadmap должен быть создан отдельным документом после утверждения этих базовых правил.
