# VK UX Flow — подбор оберега внутри VK

Версия: 0.1  
Статус: продуктовый UX-проект до разработки

## 1. Цель

Сделать подбор максимально коротким и понятным:

```text
вход → дата → пол → результат
```

Без перехода в Telegram и без длинной анкеты.

Клиенту не показывается внутренняя матрица, scoring, резервные товары и технические термины.

## 2. Общие UX-правила

1. Пользователь получает результат максимум за 2 осмысленных шага после входа.
2. Для расчёта нужны только день/месяц и пол.
3. Год рождения не нужен; если пользователь пишет полный год, он не используется в recommendation logic.
4. Пол не угадывается — только явный выбор.
5. По умолчанию показывается 1 товар.
6. Максимум 2 — только для approved scenario `Медведь + мужчина`.
7. Не показывать «ещё 5 подходящих».
8. Не добавлять автоматически призыв «узнать больше» в каждый ответ.
9. Текст результата нейтральный: Чертог → рекомендуемый оберег → короткое объяснение.
10. Ошибка наличия не должна превращать подбор в другой оберег.

## 3. Точки входа во VK

Целевые entry points:

### A. Кнопка/пункт сообщества

Название:

```text
Подобрать оберег
```

Не использовать как основной CTA формулировку `Задать вопрос`, если VK позволяет назвать действие более конкретно.

### B. Сообщения сообщества

Пользователь может написать:

```text
13.10.1976
```

или любую фразу с корректно распознаваемой датой.

### C. VK Mini App

Открывается из сообщества и даёт визуальный flow.

### D. Ссылка/QR из внешних материалов

Если в будущем карточки товара, упаковка, рекламный креатив или сайт ведут на подбор, landing должен открывать VK/Mini App либо сообщения сообщества, а не Telegram.

## 4. Bot flow

### 4.1. Новый диалог

Первое сообщение бота должно быть коротким:

```text
Укажите дату рождения — день и месяц.
Например: 13.10
```

Допустимо принимать полный формат `13.10.1976`, потому что пользователи будут присылать его естественно.

### 4.2. После валидной даты

Бот не отвечает длинной промежуточной справкой.

Следующий шаг:

```text
Для кого подбираем оберег?

[ Мужчине ] [ Женщине ]
```

### 4.3. Результат

Структура:

```text
Для даты {DD.MM} рекомендуем:

{gender_line_1}
{optional_gender_line_2}

{neutral_reason}
```

Однако если пол уже выбран, клиенту не обязательно показывать оба пола. В production bot flow предпочтителен персональный вариант:

```text
Для даты 13.10 рекомендуем оберег «Родимич».

Эта дата относится к Чертогу Щуки, который связывают с родом, семьёй, мудростью и ответственностью за близких.
```

Формат «Мужчине / Женщине» полезен для ручных ответов продавца в вопросах и комментариях, но персональный бот уже знает выбранный пол.

### 4.4. Actions после результата

Минимум:

```text
[ Посмотреть оберег ]
[ Подобрать снова ]
```

Дополнительно, если нужно:

```text
[ Написать продавцу ]
```

Не добавлять 5–7 кнопок.

## 5. Mini App flow

### Экран 1 — старт

```text
КРОВЬ И ПЕСОК

Подобрать оберег
по дате рождения

[ Начать подбор ]
```

### Экран 2 — дата

UI должен спрашивать только день и месяц.

Варианты:

- два select/input `День` и `Месяц`;
- календарный picker без обязательного года.

Текст:

```text
Укажите день и месяц рождения
```

CTA:

```text
[ Продолжить ]
```

### Экран 3 — пол

```text
Для кого подбираем?

[ Мужчине ]
[ Женщине ]
```

Никаких предвыбранных значений.

### Экран 4 — результат

Пример:

```text
Ваш Чертог — Раса

Даждьбог

Для этой даты рекомендуем оберег «Даждьбог».
Эта дата относится к Чертогу Расы, покровителем которого считается Даждьбог.

[ Посмотреть оберег ]
[ Подобрать снова ]
```

Финальный copy будет утверждаться отдельно.

### Экран 4B — два результата

Только `Медведь + мужчина`:

```text
Ваш Чертог — Медведь

1. Сварог
2. Медвежья лапа

[ Сварог ]
[ Медвежья лапа ]
[ Подобрать снова ]
```

UI не должен визуально превращать второй результат в «менее подходящий товар из каталога». Нужно показать два разных основания:

- покровитель Чертога;
- символ Чертога.

## 6. Manual answer mode

Помимо автоматического flow нужен удобный формат для владельца/менеджера, когда вопрос приходит как обычный текст и ответ даётся вручную.

### Если пол неизвестен

Можно отвечать сразу двумя гендерными строками, но максимум по одному товару на пол.

Пример структуры:

```text
Для даты 13.10.1976 рекомендуем:

Мужчине — оберег «Родимич».

Женщине — оберег «Макошь».

Эта дата относится к Чертогу Щуки, который связывают с родом, семьёй, мудростью и ответственностью за близких.
```

### Если пол известен

Показывается только релевантный вариант.

## 7. Parsing rules для Bot Adapter

Минимально поддерживаемые формы:

```text
13.10
13.10.1976
13/10
13/10/1976
13-10
13-10-1976
```

Допускается whitespace вокруг даты.

Не делать агрессивный NLP, если в сообщении две даты.

Пример:

```text
Я 13.10, жена 20.11
```

→ бот должен попросить выбрать одну дату/одного человека, а не угадывать.

## 8. Validation UX

### Некорректная дата

```text
Не удалось распознать дату. Укажите день и месяц, например 13.10.
```

### Несуществующая дата

```text
Такой даты нет. Проверьте день и месяц и отправьте ещё раз.
```

### 29.02

Принимается без вопроса о годе и относится к Волку по product calendar V1.

## 9. Unavailable UX

Смысловая рекомендация сохраняется.

Пример:

```text
Для вашей даты рекомендуем оберег «Даждьбог».

Сейчас не удалось подтвердить его наличие.

[ Написать продавцу ]
[ Подобрать снова ]
```

Запрещено:

```text
«Даждьбога нет, зато купите Алатырь»
```

без отдельной approved fallback policy.

## 10. Human handoff

Пользователь может запросить человека после результата или при проблеме.

Bot state:

```text
HUMAN_HANDOFF
```

После перехода в handoff бот не должен автоматически отвечать на каждое сообщение, пока оператор не завершил режим либо не истёк defined timeout.

Конкретная механика зависит от выбранной VK-интеграции и будет проверена в implementation milestone.

## 11. Возврат пользователя

Кнопка:

```text
Подобрать снова
```

полностью сбрасывает `birth_day`, `birth_month`, `gender` текущей session и начинает flow заново.

Ранее выданный `result_id` остаётся в audit logs.

## 12. Аналитическая воронка

```text
flow_started
→ date_submitted
→ gender_selected
→ result_shown
→ product_action_clicked
```

Отдельно:

```text
validation_error
human_handoff_requested
product_unavailable_shown
start_over_clicked
```

Главная продуктовая метрика первого этапа — не продажи конкретного оберега, а прохождение:

```text
started → result_shown
```

Потому что сначала нужно доказать, что подбор понятен и люди его заканчивают.

## 13. Не делать в V1

- свободный чат с AI вместо детерминированного flow;
- запрос имени;
- запрос года рождения как обязательного поля;
- запрос города;
- длинный тест личности;
- нумерологию;
- зодиак;
- предложение 3+ товаров;
- карусель всего каталога после результата;
- автоматические upsell-рекомендации в самом recommendation result;
- уход в Telegram.

## 14. Acceptance UX cases

### UC-01

Пользователь пишет `13.10.1976` → бот принимает `13.10`, спрашивает пол, не использует год.

### UC-02

`13.10 + male` → Родимич, 1 товар.

### UC-03

`13.10 + female` → Макошь, 1 товар.

### UC-04

`15.01 + male` → Сварог + Медвежья лапа, ровно 2 товара.

### UC-05

`15.01 + female` → Сварог, 1 товар.

### UC-06

`15.03 + any gender` → Велес; Медвежья лапа не показывается.

### UC-07

Невалидная дата не меняет state на `WAITING_GENDER`.

### UC-08

`Подобрать снова` очищает текущий selection и возвращает к вводу даты.

### UC-09

Bot и Mini App на одинаковом input показывают один semantic result.
