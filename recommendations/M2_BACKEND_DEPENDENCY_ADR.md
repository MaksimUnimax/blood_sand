# M2 Backend Dependency ADR

Версия: 0.2  
Статус: **PRE-M2 DEPENDENCY AUTHORITY**  
Дата проверки: 2026-08-29

## 1. Назначение

Этот ADR фиксирует backend technology/dependency baseline и воспроизводимый dependency-lock workflow до первого M2 runtime commit.

Он является **OUR ARCHITECTURE DECISION**, а не VK platform contract.

Primary sources used:

```text
FastAPI official docs / PyPI verified project
Pydantic official/PyPI verified project
Uvicorn official/PyPI verified project
HTTPX official/PyPI verified project
Astral uv official docs / PyPI verified project
```

No dependency or lock tool is selected from memory or an unversioned tutorial.

---

## 2. Python baseline

Project architecture baseline:

```text
Python >= 3.11
```

This is our project decision.

Current researched dependencies all have upstream minimums at or below this baseline:

```text
FastAPI 0.141.1 → Python >=3.10
Uvicorn 0.52.4 → Python >=3.10
Pydantic 2.13.5 → Python >=3.9
HTTPX 0.28.1 → stable release selected
uv 0.12.7 → Python >=3.8 when installed from PyPI
```

Before M2 implementation, local/server interpreter must be recorded:

```text
python3 --version
```

If below 3.11:

```text
M2_RUNTIME_BASELINE = BLOCKED
```

Do not silently lower project baseline just because a server has an older interpreter.

---

## 3. Direct M2 runtime/test dependencies

Freeze direct versions for M2:

```text
fastapi==0.141.1
uvicorn==0.52.4
pydantic==2.13.5
httpx==0.28.1
```

Why explicit Pydantic pin although FastAPI depends on it:

- request/error serialization is part of our HTTP contract;
- validation behavior must not drift because of an unrelated resolver update;
- M2 tests should run against one reviewed Pydantic version.

Why HTTPX is explicit in M2:

- FastAPI/Starlette test tooling uses HTTPX;
- later VK adapter may use it, but M2 itself must not call VK;
- selecting stable `0.28.1` avoids current HTTPX `1.0.dev*` prerelease line.

---

## 4. Dependency manager / lock tool

Freeze tooling version:

```text
uv==0.12.7
```

Research-time official state:

```text
uv 0.12.7
released 2026-08-27
Production/Stable
universal project lockfile supported
```

`uv` is tooling, not an application runtime dependency imported by product code.

Why selected:

- official FastAPI documentation currently recommends uv in project workflows;
- uv has an explicit project lockfile `uv.lock`;
- official uv documentation says `uv.lock` contains resolved exact versions and should be checked into version control;
- `uv sync --locked` and `uv run --locked` fail if project metadata and lockfile are out of sync instead of rewriting the lock;
- upgrades require an explicit lock/update action.

Do not use moving unpinned `uv latest` as a production/CI tooling contract.

---

## 5. Project dependency files

M2 project setup must use:

```text
pyproject.toml
uv.lock
```

`pyproject.toml` declares:

```text
requires-python = ">=3.11"
```

and the exact reviewed direct dependency pins from this ADR.

`uv.lock` is generated by uv and committed to Git.

Do not hand-edit `uv.lock`.

No parallel authoritative `requirements.txt` is required for normal project installation. An exported requirements file may be produced later for a specific deployment consumer, but it is derived from `uv.lock`, not a second independently maintained source of truth.

---

## 6. Lock creation and normal install contract

Intentional initial/update operation:

```text
uv lock
```

Normal CI/server/environment synchronization:

```text
uv sync --locked
```

Normal project test/run commands:

```text
uv run --locked ...
```

Official uv behavior: `--locked` checks that the lockfile is current and errors instead of updating it.

Forbidden in ordinary deployment/test execution:

```text
uv lock --upgrade
uv sync --upgrade
uv run --upgrade
```

Dependency upgrades are explicit review operations only.

---

## 7. Python interpreter management boundary

By default, uv is capable of downloading Python automatically when needed.

That is NOT desired as an implicit production/CI behavior for this project.

Production/CI/server policy:

```text
UV_PYTHON_DOWNLOADS=never
```

or an equivalent current uv setting/flag that completely disables managed-Python downloads.

The host must already have an approved Python >=3.11 interpreter.

Reason:

- runtime interpreter changes must be an infrastructure decision;
- a dependency sync must not silently download/switch the server Python;
- failure to find a compliant interpreter should fail deployment clearly.

Local developer environments may intentionally use uv-managed Python only through an explicit documented developer action; that does not change production policy.

---

## 8. FastAPI install mode

Use base package:

```text
fastapi==0.141.1
```

Do NOT use by default:

```text
fastapi[standard]
```

Reason: current FastAPI documentation says the `standard` extra includes additional optional tools such as Uvicorn standard extras and FastAPI CLI/cloud-related packages. This project wants a deliberately minimal, explicit server dependency set.

Uvicorn is pinned separately.

No FastAPI Cloud deployment dependency belongs in this product architecture.

---

## 9. Uvicorn mode

Use explicit:

```text
uvicorn==0.52.4
```

Do not require `uvicorn[standard]` unless a later measured deployment need justifies the extra runtime dependencies.

Production TLS termination remains outside application process behind the selected HTTPS proxy/load balancer.

Development/reload behavior is not production configuration.

---

## 10. HTTPX stability boundary

Research-time PyPI state:

```text
HTTPX stable latest = 0.28.1
HTTPX 1.0.dev* = prerelease
```

Therefore:

```text
httpx==0.28.1
```

is the M2 baseline.

Do not opt into 1.0 prerelease without a separate compatibility ADR and passing test suite.

## 11. Reproducible install gate

Exact direct versions are necessary but not sufficient.

Before M2 application source is committed:

1. create/update `pyproject.toml` using exact direct pins;
2. generate `uv.lock` with **uv 0.12.7**;
3. commit both files;
4. recreate a clean project environment from the committed lock using `uv sync --locked` with Python downloads disabled;
5. run all existing M1 tests through `uv run --locked`;
6. prove no lockfile modification occurred during sync/test;
7. only then begin the M2 application-code slice.

If clean locked install or M1 regression fails:

```text
M2_CODE_GATE = BLOCKED
```

---

## 12. Tool bootstrap boundary

The mechanism used to place the exact `uv 0.12.7` executable on a host must itself be explicit and verifiable.

Allowed examples include an approved package/install method pinned to `0.12.7`.

Forbidden deployment pattern:

```text
install latest uv
```

without checking its version.

Required verification:

```text
uv --version
→ exactly 0.12.7
```

Do not run `uv self update` during application deployment.

---

## 13. Intentionally not selected for M2

Do not add merely because common FastAPI examples use them:

```text
SQLAlchemy
Alembic
PostgreSQL driver
Redis/Celery
Jinja
python-multipart
orjson/ujson
pydantic-settings
JWT library
OAuth library
FastAPI Cloud CLI
```

M2 Recommendation API needs none of these.

M3 VK state persistence uses stdlib `sqlite3` by current implementation architecture; its migration layer is project-owned, not SQLAlchemy/Alembic by default.

M5 frontend is a separate dependency authority.

---

## 14. Configuration strategy

M2 does not need an external settings library.

Use a small typed application configuration boundary built from:

```text
stdlib os.environ / explicit constructor input
```

with startup validation.

No secrets are required for M2 Recommendation API itself.

M3/M5 later add platform secrets under their own configuration authority.

---

## 15. Test dependency policy

Prefer testing through installed runtime dependencies already required by the service.

HTTP API contract tests may use:

```text
FastAPI/Starlette TestClient or HTTPX ASGI transport
```

provided the exact test method is compatible with pinned `httpx==0.28.1`.

Do not add pytest solely because it is popular if the current repository remains on `unittest`; preserve the existing test convention unless there is a concrete test capability gap.

Existing M1 tests use Python `unittest` and must continue passing.

---

## 16. Upgrade policy

Dependency upgrades are not automatic semantic changes.

Future upgrade procedure:

```text
check primary release notes
→ update direct pin intentionally
→ run explicit uv lock/update operation
→ inspect uv.lock diff
→ clean uv sync --locked
→ full M1/M2 regression
→ inspect error/schema/OpenAPI changes
→ commit as explicit dependency upgrade
```

Never allow floating runtime dependencies or lock tooling to update during ordinary deployment.
