# Ozon Bridge — roadmap завершения полного read-покрытия

Дата: **2026-08-29**  
Статус: **ACTIVE IMPLEMENTATION ROADMAP**  
Рабочая линия: `repair/ozon-v2-b1-stocks-warehouse-2026-08-29`

## 1. Конечная цель

Довести Ozon Bridge до состояния, в котором ИИ имеет доступ ко **всем актуальным допустимым операциям чтения** двух публичных API Ozon, используемых проектом:

1. **Ozon Seller API** — полный текущий Swagger: **463 операции**.
2. **Ozon Performance API** — имеющийся точный Swagger: **48 HTTP-операций**.

Для каждой операции обоих API должно быть принято и записано одно окончательное решение. В финальной сборке не должно оставаться неизвестных, неразобранных или случайно пропущенных операций.

Цель — не заданное заранее количество включённых методов. Цель — проверить **весь контракт каждого API** и включить все операции, которые действительно являются допустимым чтением данных.

Изменяющие данные операции остаются недоступны ИИ.

## 2. Неподвижные правила

### 2.1 Один явный запрос Bridge — максимум один физический запрос к Ozon

Одна команда ИИ к Bridge не должна скрыто превращаться в несколько запросов к Ozon.

Запрещены внутри одной команды Bridge:

- скрытая пагинация;
- скрытые повторные запросы;
- скрытый fan-out по идентификаторам;
- скрытый polling;
- скрытое продолжение workflow.

Это **не означает**, что пользователь обязан вручную управлять многошаговым API-процессом. ИИ может сам последовательно выполнять несколько явных команд Bridge в рамках одной пользовательской задачи.

### 2.2 Отчёты и другие многошаговые read-workflow

Пользователь ставит бизнес-задачу, например просит получить или проанализировать отчёт. Пользователь не обязан знать техническую последовательность API.

Если конкретный контракт Ozon требует несколько шагов, ИИ самостоятельно ведёт workflow через последовательные явные команды Bridge.

Пример только как принцип, а не как обязательная схема для всех методов:

1. ИИ вызывает операцию создания/запроса отчёта.
2. Bridge возвращает результат операции и, если применимо, код/ID и допустимый следующий технический шаг.
3. ИИ отдельной командой вызывает требуемую по контракту проверку/получение результата.
4. Цепочка продолжается столько шагов, сколько реально определено контрактом конкретного метода.

Нельзя заранее навязывать всем отчётам схему `create -> status -> result`. Для каждой операции используется фактический Swagger/контракт Ozon.

Главное ограничение: **каждый физический запрос к Ozon соответствует отдельной явной команде ИИ к Bridge**, но управление этими техническими шагами выполняет ИИ, а не пользователь.

### 2.3 Personal Data

Существующий механизм Personal Data сохраняется как правильный контракт и не переделывается на другую модель.

Для операции, которая требует разрешения на личные данные:

**Personal Data OFF:**

- запрос блокируется до обращения к Ozon;
- физический запрос к Ozon = 0;
- Bridge возвращает ИИ понятный результат о том, что для получения этих данных необходимо включить Personal Data в настройках;
- включение чека не должно автоматически повторять ранее заблокированную команду.

**Personal Data ON:**

- ИИ явно повторяет нужную команду;
- выполняется ровно допустимый запрос;
- данные операции могут быть возвращены согласно принятому Personal Data контракту.

Этот механизм уже был принят и проверен в B0 и использован в B9/B17. При восстановлении полного read-покрытия требуется не придумывать новый механизм, а убедиться, что **каждая операция, которой он нужен, правильно к нему привязана**.

### 2.4 Performance API является обязательной частью полного read-покрытия продукта

Performance API технически является отдельным API/provider, но не является необязательной побочной работой.

Полная цель продукта включает:

- все допустимые Seller API reads;
- все допустимые Performance API reads.

Старый B6 Performance Read Core — полезная принятая работа, но это только часть Performance-покрытия. Имеющийся Performance Swagger содержит **48 HTTP-операций**. Все 48 должны быть разобраны; все допустимые read/read-workflow операции должны быть реализованы, а mutations — заблокированы.

### 2.5 Никакой новой бесконечной B-нумерации

Запрещено выбирать новый метод только потому, что он обнаружен как очередной gap, и объявлять его новым самостоятельным B50/B51/... этапом.

Источник порядка работы — этот roadmap и полный контрольный список API.

## 3. Обязательный master-checklist

До дальнейшего массового добавления методов должен быть создан единый машинно-читаемый/проверяемый список:

- **463 строки Seller API**;
- **48 строк Performance API**.

Для каждой операции минимум фиксируются:

- API/provider;
- HTTP method + fixed path;
- назначение простым языком;
- current/deprecated;
- read / read-workflow / mutation / unresolved;
- уже реализована в Bridge или нет;
- если реализована — откуда берётся проверенный код/контракт;
- требует ли Personal Data;
- entitlement/subscription rule, если есть;
- quota/rate-limit rule, если есть;
- pagination model;
- workflow role, если операция многошаговая;
- итоговое действие: сохранить / перенести / добавить / заменить / заблокировать / дополнительно исследовать.

Финальный gate: **ни одной строки без окончательного решения**.

### Шаг 5 — реализовать все допустимые Seller read-workflow / report / document операции

Пройти все Seller операции, которые читают существующие данные через создание/получение отчёта, документа или другого observational workflow.

Для каждого метода реализовать **ровно ту последовательность**, которую задаёт его фактический контракт.

ИИ управляет последовательностью команд. Пользователь не обязан вручную командовать каждым техническим шагом.

Bridge не выполняет скрытый polling/retry/fanout.

Файлы/документы должны передаваться через безопасный предусмотренный результат, а не через произвольное скачивание URL, заданного ИИ.

**Статус: NOT COMPLETE.**

### Шаг 6 — завершить Performance API coverage по всем 48 операциям

Взять точный Performance Swagger и пройти **48/48** операций.
