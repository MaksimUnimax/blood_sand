# Ozon Bridge Patch A.5 — Resume without prompt + provider-status separation

Branch: `fix/ozon-work-resume-provider-status-separation-2026-08-24`

Base closure commit: `051967779a37cffb2eacc830dcfd0b604d966ce2`

## User-observed defects

1. After opening/starting work in a new chat the popup could show a red stale banner such as `CONVERSATION_NOT_CONFIRMED: NaN` even while the same popup simultaneously showed a confirmed binding and an active Work-session.
2. With a confirmed explicit binding and `Work-session: inactive`, `Показать кнопку` was disabled. The only way to return to `active_visible` was `Начать работу`, which sends the initial AI prompt again.
3. `Завершить работу` deleted the explicit conversation binding, preventing a clean later resume of the same AI conversation without a new Start prompt.

## Exact red-status root cause

The popup calls `OZ_RESOLVE_POPUP_CONTEXT` even for a supported brand-new AI chat that has no persistent `conversation_id` yet. `resolvePopupContext()` in the service worker then calls `resolveConfirmedConversationKey()` and correctly throws `CONVERSATION_NOT_CONFIRMED`.

The bug is not that this fail-closed error exists. The bug is that the generic `chrome.runtime.onMessage` catch persisted every runtime/UI error through `setStatus()` into global `KEYS.LAST_STATUS`.

`KEYS.LAST_STATUS` is rendered by the popup as the last API/provider status before the normal binding/session banner. It was therefore possible for a transient new-chat identity error to survive a later successful Start/binding and remain the primary red banner.

The literal string `NaN` is not emitted by any `CONVERSATION_NOT_CONFIRMED` source in the accepted A.4 production tree: all such sources use fixed human-readable messages. Therefore `NaN` is a contaminated/legacy persisted LAST_STATUS payload. Patch A.5 makes that payload semantically ineligible for provider-status display rather than trying to special-case the string.

## Status architecture fix

`LAST_STATUS` is now explicitly provider-scoped:

- `setStatus()` writes `scope: "provider"`.
- `commonPublicSettingsFields()` exposes `last_status` only when `scope === "provider"`.
- generic extension/message failures are no longer written to provider LAST_STATUS; they are recorded as diagnostic `EXTENSION_MESSAGE_FAILED` and returned directly to the caller.
- old unscoped/contaminated LAST_STATUS records are ignored automatically.

This separates provider/API health from conversation lifecycle/runtime errors instead of clearing one particular error string.

## Work-session Resume architecture

Patch A.5 adds a distinct `OZ_WORK_RESUME` lifecycle operation. It is not a `skip_prompt` flag on Start.

Resume requirements:

- current session must be `inactive`;
- current tab identity must match the exact conversation key;
- the conversation must still have the explicit binding;
- no active manual operation may remain;
- state transition is the already-legal `inactive -> binding -> active_visible`;
- command acceptance is enabled;
- content receives `OZ_WORK_APPLY_VISIBILITY visible:true`;
- no `OZ_WORK_SEND_INITIAL_PROMPT` and no prompt send path is used;
- diagnostic `WORK_SESSION_RESUMED_WITHOUT_PROMPT` is recorded;
- no external Ozon request is generated by Resume.

Popup behavior:

- `inactive + bound` -> `Показать кнопку` is enabled and dispatches `OZ_WORK_RESUME`;
- `active_hidden` -> the same button dispatches existing `OZ_WORK_SHOW`;
- `active_visible` -> the same button becomes `Убрать кнопку` and dispatches existing `OZ_WORK_HIDE`.

`Начать работу / Отправить начальный prompt` remains a separate explicit AI-initialization action.

## Finish binding semantics

`OZ_WORK_FINISH` still:

- closes command acceptance;
- hides/removes current Ozon UI;
- terminalizes the current manual operation safely;
- stops Autorun if one exists using the existing logic;
- transitions `finishing -> inactive`.

It no longer deletes the explicit conversation binding. It records `WORK_SESSION_FINISHED_BINDING_PRESERVED` and returns `binding_preserved:true`.

This makes binding (which AI conversation is connected) independent from Work-session activity (whether Ozon controls are currently active).
