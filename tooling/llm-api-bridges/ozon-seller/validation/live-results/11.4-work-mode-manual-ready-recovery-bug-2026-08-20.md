# Ozon Bridge v0.1.19 — live result 11.4

Date: 2026-08-20
Surface: ChatGPT Work mode
Scenario: Manual bridge readiness after the first completed result delivery
Status: BUG / DEFERRED REPAIR

## Observed behavior

1. On initial page/state synchronization there is no active Manual operation, so the Ozon buttons are enabled.
2. The first Ozon block can be executed.
3. Manual admission sets the bridge globally busy.
4. After delivery, Work mode does not expose the completion Voice/Microphone control expected by the current ChatGPT delivery classifier. Its composer shows the persistent dictation microphone plus a disabled Send arrow instead of the terminal Voice-ready control used by the existing completion path.
5. The delivery state is therefore not confirmed back to ready.
6. All Ozon buttons remain disabled, including buttons attached to other code blocks.

## Code-level boundary

The button state is controlled by:

```js
const ready = manualEnabled && manualBridgeReady;
record.button.disabled = !ready || record.in_flight === true;
```

The first click sets `manualBridgeReady=false` during Manual batch admission. The current recovery path restores readiness only after a recognized delivery-completion control/state. Work mode does not satisfy that classifier, leaving the previous Manual operation in `delivering` / `ready=false`.

## Verdict

**BUG / WORK MODE UI-COMPATIBILITY GAP / DEFERRED REPAIR**

This is not an Ozon provider failure and not a command-schema failure. It is a downstream ChatGPT Work-mode delivery-state compatibility bug. Do not fix it during the current append-only live test pass; preserve it as the final observed test and repair it later with focused Work-mode composer/control coverage.
