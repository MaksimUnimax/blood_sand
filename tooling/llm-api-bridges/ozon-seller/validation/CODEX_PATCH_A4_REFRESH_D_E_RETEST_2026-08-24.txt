PATCH A.4 ACCEPTANCE MODEL
The governing lifecycle spec permits a service-worker runtime that is genuinely `renewed OR reinitialized` through a supported lifecycle mechanism.

A.4 deliberately chooses REINITIALIZED, not physical extension reload.

Therefore during Refresh the expected physical behavior is:
- the extension service-worker target may remain the same;
- `WORKER_SESSION_ID` MUST remain the same during that current-conversation Refresh;
- no `chrome.runtime.reload()` is expected;
- no new service-worker target is required.

The required recovery proof instead is:
1. durable recovery is prepared while the session is `recovering` and command acceptance is closed;
2. old Work-session runtime generation is recorded;
3. a different new Work-session runtime generation is generated;
4. diagnostic `WORK_SESSION_REFRESH_RUNTIME_REINITIALIZED` contains same physical `worker_session_id`, old generation and new generation with old != new;
5. the product itself reloads the SAME owner AI tab;
6. page observer proves a real same-tab document `loading -> complete` cycle without harness reload/navigation;
7. diagnostic `WORK_SESSION_REFRESH_TAB_RELOAD_COMPLETED` is emitted for the exact recovery/tab/new generation;
8. the fresh manifest content script reconnects on the same supported conversation URL/identity;
9. `OZ_WORK_RUNTIME_RENEW` handshake acknowledges exactly the new generation and fresh `ui_record_generation`;
10. `WORK_SESSION_REFRESH_RESUMED` contains old generation, new generation, old != new, unchanged physical `worker_session_id`, and the correct restored state;
11. durable recovery is removed;
12. no command replay and no provider request occurs.

A physical worker target change is NOT an A.4 requirement and must not be invented as one.
