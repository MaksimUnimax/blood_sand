# CAP-12 — Returns / cancellations — SETUP

Status: ACTIVE

Canonical job:

`Какие возвраты сейчас есть у меня на Ozon, по каким товарам и в каких статусах/состояниях они находятся? Отдельно разберись с отменами: не подменяй справочник возможных причин отмены списком фактически отменённых заказов и не выдумывай отмену без order/posting evidence.`

Capability target: prove the worker recognizes returns/cancellations as a dedicated Ozon surface, can inspect current return records, and preserves the semantic boundary between actual return/cancellation evidence and reference-only cancellation reason dictionaries.

Active registry authority:
- `returns_list` -> `POST /v1/returns/list`, READ_SAFE, dedicated `returns_cancellations/returns` surface; current return information for FBO/FBS.
- cancellation surfaces include read-safe reason dictionaries plus point checks requiring known `order_number` / `posting_number`.
- `conditional_cancellation_list` is personal-data-gated and must not be used implicitly.

Contract for `returns_list`:
- params: `filter?`, `limit`, `last_id?`;
- `limit` maximum 500;
- next page, if any, must be an explicit separate command;
- optional filters include one temporal field at a time plus order/posting/product/status selectors.

Frozen method:
1. Start with one broad current `returns_list` page at `limit=500` and no invented selectors.
2. Inspect returned status/reason/product/posting evidence and explicit continuation state.
3. If pagination is required, continue explicitly; do not silently truncate.
4. Only after return evidence is understood, use the minimum cancellation read needed to answer the cancellation part. A generic `cancel_reason_list` is reference data only and must never be represented as actual cancelled orders.
5. If no safe account-wide actual-cancellation surface exists without a known order/posting identifier, surface that coverage boundary honestly instead of fabricating cancellations.

Checkpoint: `CAP_12_ACTIVE_RUN_1_NEXT`
