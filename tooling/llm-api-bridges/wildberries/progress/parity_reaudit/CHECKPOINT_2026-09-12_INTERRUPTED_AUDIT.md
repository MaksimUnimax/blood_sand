## 5. Точное следующее действие

После публикации этой контрольной точки, обновления общего журнала/cursor и remote readback продолжать существующий корректирующий parity-проход, а не начинать новый проект.

Первый рабочий блок: прочитать полностью `SUPERSEDING_PATCH_AUTHORITY_2026-09-12.md` и относящийся к popup раздел `WB021_PARITY_GAPS_2026-09-12.md`; сверить действующие правила патчей; зафиксировать точные Ozon и WB исходники/refs для сравнения popup, кнопок, обработчиков и state synchronization. До изменения кода сохранить отдельный результат этого блока: симптом → доказанная причина → Ozon-исправление → фактическое WB-расхождение → связанные зависимости → воспроизводящий тест → план переноса.

Далее выполнять корректирующий provider-neutral parity-патч по superseding authority с сохранением каждого материального блока и полного WIP, а не только конечной сборки. WB021 baseline и старые свидетельства не переписывать. Исправленные классификации добавлять явно.

Не выполнять дополнительные WB post-install проверки или R1–R8/provider characterization до выполнения действующего gate. Не копировать Ozon-specific API значения в WB. Не запускать реальные marketplace calls ради сохранения журнала.

## 6. Периодичность checkpoint

После каждого законченного смыслового блока, каждого обнаруженного дефекта и каждой ограниченной группы тестов сохранять результат. При длинном чтении делать промежуточную запись не позднее пяти содержательных read/search вызовов, даже если блок ещё не завершён. Для большого файла записывать path, ref/blob SHA, прочитанные диапазоны строк и следующий диапазон. Не отмечать частичное чтение как полное.

Каждая запись содержит: цель блока; фактически сделанное; проверенные источники; результат/FAIL/неопределённость; реальные изменённые файлы и diff; test runner и stdout/stderr/exit code при наличии; оставшуюся работу; точное следующее действие; состояние публикации.

Перед долгим действием и завершением ответа — checkpoint. Тестовые результаты писать по мере выполнения с flush/fsync. Ошибка теста не стирает предшествующие результаты. После записи в GitHub — readback; только после успешного чтения сообщать «сохранено и проверено». При неопределённом результате записи сначала проверить remote, не повторять запись вслепую. Force push запрещён.

Этот checkpoint-проход: новых runtime-изменений 0; новых тестовых прогонов 0; реальных WB/Ozon provider calls 0; бизнес-изменений 0. Это сохранение хода работы, не исправленная сборка.
